## Why two systems

The operational EHR is built around a single discipline: the chart must be fast and correct for the clinician who is using it right now. Every architectural decision in the operational system is downstream of that discipline. The schema is normalized for fast in-place updates. The indexes are tuned to one-patient queries. The hardware is sized for short transactions at high concurrency. The backup posture is sized for recovery within an RTO that the hospital has agreed to. Everything in the operational EHR is structurally about *transactions*: small, frequent, in-place reads and writes that have to commit reliably and quickly.

Analytics is a different discipline. The question *what is the average CRP across our seropositive RA cohort in the last twelve months* is a query that scans millions of rows. It does not need sub-second response. It does not need write capacity. It cannot tolerate the operational schema, which makes the query much harder than it needs to be by storing the same fact in multiple normalized tables.

So the field built a second system, dedicated to the analytical workload. That system is the **clinical data warehouse**. It is the same data, in a different shape, on different hardware, with different priorities.

## OLTP and OLAP

The clean way to name the two workloads is by their archetype:

- **OLTP (online transaction processing)** is the workload of the chart. Many users, many small reads and writes, sub-second response, primary-key lookups, in-place updates. Examples beyond the EHR: ATMs, e-commerce checkout flows, airline reservation systems. The relational model, normalized to third or fourth normal form, with B-tree indexes on the keys the application uses, is the canonical OLTP design.
- **OLAP (online analytical processing)** is the workload of the warehouse. Fewer users, occasional but very large reads, multi-second to multi-minute response acceptable, scans across millions of rows, joins across many tables. Aggregations like sums, averages, percentiles. The star schema (one fact, several dimensions) is the canonical OLAP design.

OLTP systems are usually row-oriented (rows are stored together on disk because the application reads or writes one row at a time). OLAP systems are increasingly columnar (columns are stored together because the analytical query touches a few columns of many rows at a time). The columnar layout is the single biggest technical reason modern analytical warehouses outperform classic OLTP databases at scale.

This is the foundation. The CDW is an OLAP system that lives next to the OLTP EHR. Course 00 of this curriculum introduces the distinction at the field-orientation level; this track is where it pays off.

## How data crosses the bridge

The bridge between the EHR and the warehouse is a **pipeline**. The pipeline has three operations regardless of which order they happen in:

- **Extract** data from the source. For Epic, this usually means reading from Clarity (Epic's nightly relational dump of Chronicles, its operational data store) or from Caboodle (Epic's bundled warehouse, which is loaded from Clarity). For Oracle Health, it means reading from one of the Cerner Millennium replicas.
- **Transform** the data. Clean up duplicates. Pivot EAV flowsheet rows into wide measurement tables. Map vendor-specific codes to standard codes. Conform date and time formats. Resolve patient-merge events. Compute derived fields (DAS28 from its components, for example).
- **Load** the transformed data into the warehouse's target tables.

The classic pattern is **ETL** (extract, transform, load). The newer pattern is **ELT** (extract, load, transform). The difference is whether transformation happens before loading (on an intermediate server) or after loading (using the warehouse's own compute). ELT became popular when warehouse storage got cheap enough to keep raw landing data around and warehouse engines got fast enough to transform large tables in place. ELT keeps lineage traceable in a way ETL does not, because the raw load is still queryable months later.

A real production pipeline is not one ETL job; it is a dependency graph of dozens or hundreds. Patient demographics have to load before the encounters that reference them. Encounters have to load before the lab results that reference them. Lab results have to load before the derived analytical views that aggregate them. **Orchestration** tools like Apache Airflow, Prefect, dbt, or Microsoft SSIS handle the scheduling, retries, and dependency tracking. A failure in a single early-stage job can stall the whole graph.

## Three storage architectures

Three patterns for the underlying storage matter clinically.

### Data warehouse

A traditional data warehouse is a relational database, often columnar, that holds *schema-on-write* tables. Loaded data has been transformed and conforms to a pre-defined schema. The tables are queryable with SQL. The data is clean. Examples: Oracle Exadata, Microsoft SQL Server with columnstore, Snowflake, Amazon Redshift, Google BigQuery, Teradata, IBM Db2 Warehouse.

Inside healthcare:

- **Epic Caboodle.** Epic's bundled CDW product. Ships with a defined star schema and a library of canned reports. Most Epic hospitals use it. Caboodle is a Microsoft SQL Server database under the hood, loaded by Epic-controlled ETL from Clarity.
- **Cerner CCL / HealtheIntent.** Oracle Health's analytical stack.
- **Athenahealth analytics platform.** Smaller-footprint vendor offering for the Athena base.
- **Custom CDW.** Hand-built star schemas at academic medical centers, populated by institution-owned ETL.

### Data lake

A data lake is a large object-storage bucket holding raw files. *Schema-on-read*: you dump data in (CSV, JSON, Parquet, log files, image files, FHIR bundles, ORU dumps) and impose schema at query time. Examples: Amazon S3 with Athena, Azure Data Lake Storage with Synapse, Google Cloud Storage with BigQuery external tables.

Lakes are right when:

- You have many heterogeneous source formats.
- You want to keep raw data around forever for lineage and re-runs.
- You have machine-learning workloads that want raw signal, not pre-aggregated rows.
- Cost per terabyte matters and the access patterns are scan-heavy and infrequent.

The risk with lakes is that without strong cataloging (a metadata system that documents what each file contains and when it landed), the lake degrades into a data swamp where nobody knows what each file means. The clinical practice that prevents this is **the data catalog**: a separate metadata service (Apache Atlas, AWS Glue Data Catalog, Microsoft Purview, Alation, Collibra) that tracks every file, schema, and lineage relationship in the lake.

### Lakehouse

A lakehouse is the architecture that emerged in 2020 trying to keep the best of both. Cheap object storage as the underlying physical layer (like a lake), with a transactional table layer (Delta Lake, Apache Iceberg, Apache Hudi) on top that provides ACID transactions, schemas, indexes, and time travel (like a warehouse). Vendor examples: Databricks Lakehouse, Snowflake with Iceberg tables, Microsoft Fabric.

For new clinical analytics builds in 2026, the lakehouse is increasingly the default. It supports both the OMOP / star-schema workload and the AI-training workload from a single physical storage layer, which means a hospital can stop running two parallel systems.

## The star schema in detail

The dominant logical design inside any CDW is the **star schema**, named after the shape of the entity-relationship diagram (one fact in the middle, dimensions radiating out).

The principles:

1. **Each fact table holds one kind of clinical event.** Lab results in one fact. Medication administrations in another. Encounters in a third. Vital signs in a fourth. Claims in a fifth.
2. **Each row of a fact table is one event.** The fact carries numeric *measures* (the result value, the dose, the cost), date keys, and foreign keys to the dimensions.
3. **Dimensions describe the participants in the events.** Patient, provider, location, date, drug, lab test. Dimensions are small (thousands to millions of rows) and change slowly.
4. **Surrogate keys, not natural keys.** The `patient_key` is an integer assigned by the warehouse, not the MRN. This decouples joins from the application's identifier choices and handles patient-merge events cleanly.
5. **Decoded date dimensions.** Calendar dates are joined to a `dim_date` table that pre-decodes them into year, quarter, month, day-of-week, fiscal-year, holiday-flag, and so on. Analytics groups by any of these without re-parsing strings.

The star schema is the same Kimball-style dimensional modeling that the broader BI world has used since the 1990s. The clinical adaptation is that the dimensions and facts are explicitly named for clinical concepts, the codes are clinical codes, and the time grain is clinical time.

Two important refinements:

- **Slowly changing dimensions (SCDs).** When a patient's address changes, or a provider's department changes, the dimension table needs a strategy. The most common pattern is *SCD Type 2*: keep the old row, add a new row with the new attribute, mark each row with a `valid_from` and `valid_to` date so historical fact rows can be joined back to the dimension state that was true at the time of the event.
- **Conformed dimensions.** A `dim_patient` dimension is *conformed* if it is the single source of truth for patient information across every fact table. The dim is built once, used everywhere, and any change to a patient's attributes shows up consistently in every analytical query.

## The standardized common data models

A custom hospital CDW has the property that every research analyst has to learn its specific schema. The OHDSI consortium asked the next question: what if many hospitals adopted the same schema, so a tool written once would work everywhere? That question produced **OMOP**.

Three CDMs worth knowing about (course 07 covers OMOP in depth):

- **OMOP (Observational Medical Outcomes Partnership) Common Data Model.** Standardized concept tables, standardized vocabulary mappings (the OMOP Vocabulary harmonizes hundreds of clinical coding systems into shared concept IDs), and a strict schema. A tool written for OMOP works on any institution that has mapped its data to OMOP.
- **PCORnet Common Data Model.** Same general idea, US-PCOR-specific, used by the PCORnet research network.
- **i2b2 / ACT.** An older star-schema-based CDM with strong cohort-discovery tooling, used heavily in CTSA institutions.

A mature academic medical center typically has all three at once: a vendor-bundled CDW for operations, a custom star-schema CDW for institution-specific analytics, and an OMOP or PCORnet mart for federated research. Each layer pays some loss in translation. The compensating gain is that the downstream tooling becomes substantially more capable.

## The reflex to install

When a clinician colleague asks why one query is fast and another is slow, the answer is the OLTP-OLAP split. When a vendor draws a diagram with five boxes and four arrows, every box can be placed in the operational-EHR-to-warehouse-to-research-mart stack above. When a clinical question lands on your desk and the warehouse team is backlogged, you can sketch the fact and the dimensions on the back of an envelope and propose the new analytical view without waiting on them. None of those moves require deep engineering. They require knowing the architectural shape this track has been laying out.
