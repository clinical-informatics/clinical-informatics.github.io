## The setting

In 1985 the Hospital Corporation of America had a problem. Their hospitals were buying lab analyzers, pharmacy systems, registration systems, and the early ancestors of the EHR from different vendors. Every interface between two systems was a custom build: an engineer would sit down with two vendor specifications and write code to translate one system's format into the other's. There were no shared standards. The integration cost grew faster than the value of the systems being integrated.

A group of vendors and hospitals met in 1987 to design a common message format. They wanted three things: a simple syntax that any system could parse, a stable vocabulary of message types covering the clinical events that mattered most (admit, discharge, transfer, order, result), and enough optionality that no vendor would be forced to populate fields they did not already have.

They got those three things. The standard they produced was **HL7 v2**, named after the OSI Layer 7 of the network stack (the application layer). It has been the dominant intra-hospital messaging format ever since.

The price they paid for optionality was that two valid v2 messages from two different sending systems would look nothing alike. That cost is still being paid today.

## HL7 v2 in detail

### The structure

A v2 message is a sequence of **segments**, separated by carriage-return characters. Each segment is identified by a three-letter code at the start:

- `MSH` (message header, always first)
- `PID` (patient identification)
- `PV1` (patient visit)
- `OBR` (observation request: a lab order)
- `OBX` (observation: a single result component)
- `EVN` (event)
- `DG1` (diagnosis)
- `IN1` (insurance)
- `GT1` (guarantor)
- ... about 80 standard segment types and dozens of variants.

Each segment is a sequence of **fields** separated by `|`. The fields are positional, not named. The fifth field of a `PID` segment is always Patient Name, regardless of what the message is for.

Each field is a sequence of **components** separated by `^`. A Patient Name field has components for family, given, middle, suffix, prefix.

Each component is a sequence of **subcomponents** separated by `&`. Subcomponents are used for things like coded entries with both a code and a coding system.

A `~` separates *repetitions* of a field. Patient identifiers, for example, repeat: a patient typically has both an MRN and a system-internal id, separated by `~` inside the same field.

The whole thing is a tree, encoded as flat text with four delimiter characters. The MSH segment header carries the delimiters themselves so the receiver knows how to parse: the second field of MSH is the encoding-characters field, conventionally `^~\&`.

### Message types

A v2 message is identified by its **event type code**, like `ADT^A04` or `ORU^R01`. The first part is the message family; the second part is the specific event. Some of the message families that matter:

| Family | What it is for |
|---|---|
| ADT | Admit, discharge, transfer, registration, demographics |
| ORU | Observation result unsolicited (lab and other results) |
| ORM | Order message (place a new order) |
| MDM | Medical document management (clinical notes, reports) |
| SIU | Scheduling information unsolicited |
| BAR | Billing account record |
| RDE | Pharmacy order |
| RAS | Pharmacy administration |
| VXU | Vaccination record update (for immunization registries) |

ADT and ORU together carry most of the volume in a working hospital. A hospital that admits twenty thousand patients a year generates millions of ADT messages a year (because every demographic update, every bed change, every encounter event fires an ADT). ORU traffic scales with lab volume, which means it scales with everything else.

### The interface engine

No production hospital connects systems point-to-point. Instead, every system talks to an **interface engine** (Rhapsody, Mirth Connect, Cloverleaf, Intersystems HealthShare). The interface engine receives all incoming messages, applies routing rules, transforms them as needed for each receiver, and fans them out. It is the post office of the hospital's clinical network. When something goes wrong with inter-system traffic, the interface engine is where the operations team looks first.

The interface engine is also where most of the heavy v2-to-FHIR translation work happens in 2026. The lab still emits ORU. The internal EHR still consumes ORU. But a CDS Hooks app or a patient-facing portal expects FHIR. The interface engine is the thing converting ORU into FHIR Observation resources on the way out.

## CDA: documents instead of messages

By the early 2000s, HL7 had recognized that v2 was insufficient for one specific use case: shipping an entire clinical document (a discharge summary, a consultation note, a referral packet) from one provider to another. v2 had been extended with the MDM message family for clinical documents, but MDM was structurally a *transport* for an attached blob, not a *format* for the document itself.

HL7 v3 was the broader effort to fix v2's looseness with a strict object model (the Reference Information Model, or RIM). The RIM defines about a dozen base classes (Act, Entity, Role, Participation) and a typing discipline. v3 messages are XML documents constructed from RIM classes. The discipline is tight; the learning curve is steep.

Most of v3 never gained adoption. The clinicians and developers who tried to use it complained that the RIM was harder to learn than was justified by the payoff, and the messages were bulky and hard to read. v3 lives on in two places: in some European national health-IT programs that bet heavily on it, and in CDA.

**CDA** (Clinical Document Architecture) is v3 adapted to the document use case. A CDA document is a single XML file with three layers:

1. **Header.** Document metadata: type code, effective time, patient, author, custodian, source organization, signatures.
2. **Narrative body.** A human-readable rendering of the document content, structured as sections with titles and HTML-style content. This is what a reading clinician sees.
3. **Structured entries** (optional). Inside each narrative section, the standard allows machine-readable entries with standard codes. A Problem List section's narrative table can be paired with `<entry>` elements containing SNOMED CT and ICD-10 coded problems.

The big practical instance of CDA in US healthcare is the **Continuity of Care Document (CCD)**, codified by the C-CDA implementation guide. Meaningful Use Stage 2 (2014) required US-certified EHRs to be able to generate and consume CCDs, which made CDA ubiquitous. Every major US EHR can spit out a CCD on request; every major EHR can take one in.

CDA's three quiet failures:

1. **The structured entries are optional.** A vendor can produce a CDA document with a beautiful human-readable narrative section and *empty* structured entries. Many vendors do. The receiving system gets a renderable document with no machine-readable data underneath.
2. **The narrative and the entries can disagree.** When both are populated, nothing in the standard enforces that the structured entries reflect what is in the narrative. Implementations have shipped where the entries are stale or summary-level and the narrative is the truth, or vice versa.
3. **The implementation guide is dense.** Reading the C-CDA IG and figuring out where in the template tree your Problem Concern entry should live is a multi-day exercise. Most application developers route around CDA whenever they can.

## How v2 and CDA fail differently

The failure modes of v2 and CDA are different in instructive ways:

| Failure mode | HL7 v2 | CDA |
|---|---|---|
| Optionality | Most fields optional; not all messages populate them | Structured entries are optional; many documents skip them |
| Vocabulary drift | Local lab codes show up in OBX-3 in place of LOINC | Local templates in place of standard C-CDA templates |
| Site-specific extensions | Z-segments | Custom template extensions and unusual OID arcs |
| Validation tradition | Receiver-side runtime checks | Standard requires schema validation but practical enforcement is weak |
| Document fit | Poor (MDM is a workaround) | Strong (CDA is a document standard) |
| Developer ergonomics | Acceptable once you learn the segments | Painful; the v3 RIM has a learning curve |

The pattern is the same in both cases. The standard sanctions optionality and extension, and the slack gets used. The receiving system writes local mappings to clean up the result. Those mappings are the interoperability tax of the installed base.

## What changed and why FHIR happened

By 2010 the web had matured. REST was the dominant pattern for system-to-system communication. JSON had replaced XML for most new development. OAuth had standardized how applications authenticate to other applications on a user's behalf. The clinical IT field had spent twenty-five years building HL7-specific tooling that did not match how the rest of software was being built.

Grahame Grieve (an Australian developer and HL7 board member) led the push to design a new standard that would behave like a web API. The result was FHIR (Fast Healthcare Interoperability Resources), first published as DSTU 1 in 2014.

FHIR's design decisions are reactions to v2 and CDA's pain points:

- **Resources, not messages.** A Patient is an object; an Observation is an object; you GET them from a server by URL.
- **Standard web architecture.** REST over HTTP. JSON or XML representation. OAuth for authentication.
- **Strict validation through profiles.** A profile (US Core Patient, mCODE Primary Cancer Condition) specifies which fields are required, which are must-support, which value sets apply. The standard contract is enforced at design time.
- **Extensible by design.** Need a field the base resource does not have? Add an extension with its own URL. Extensions are first-class, not site-specific tricks.

FHIR is the right answer for new development. It is also not yet the right answer for the installed base of v2 traffic, because converting forty years of internal hospital messaging is expensive. The interface engine sits in the middle, doing v2 inbound and FHIR outbound where the consumer is on the FHIR side.

## The operational consequence

When a result is not showing up on a chart, the trace runs through OBX-3 (observation identifier), OBX-5 (value), OBX-7 (reference range), and OBX-11 (status). Most of the "the lab result isn't on the chart" tickets in a working hospital come down to one of those fields being malformed in the originating ORU. Similarly, when an outside referral comes in as a C-CDA, the question is whether the structured entries inside each section match the narrative the receiving clinician is reading. The narrative is what the chart renders; the structured entries are what downstream analytics will use. They are supposed to agree. They often do not.

The reading-level fluency to do that troubleshooting is what Track 02 is for. It is unglamorous work that the interface team will respect immediately.
