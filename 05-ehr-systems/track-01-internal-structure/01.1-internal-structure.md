# 01.1 How EHRs structure data internally

A reference essay for Track 01. The notebook is interactive; this is for the read-at-your-own-pace deeper walk through the same territory.

## The renderer and the database

The screen of any EHR is a *renderer*. It is a presentation layer that runs on the clinician's workstation, talks to the EHR application server, and shows the user a curated view of a record. The renderer is what most clinicians experience as "the EHR." Underneath the renderer is the application server, and underneath the application server is a *relational database* holding the actual data.

The relational database is where the work lives. It is the part of the system that has to be true, that has to be fast for the chart, that has to be backed up nightly, and that the hospital's IT team spends most of its operational energy keeping healthy. The chart you click is the renderer; the data you act on lives in the database.

Two facts about every major US EHR are worth holding in mind:

1. The data is **relational**. Tables, rows, columns, primary keys, foreign keys, joins. The vendor's particular database engine differs (Epic runs on Caché, which is an object database that supports SQL; Oracle Health runs on Oracle; MEDITECH and Athenahealth run on Microsoft SQL Server), but the conceptual model is the same.
2. The schema is **large and stable**. A production Epic Clarity database has somewhere between three hundred and a few thousand tables, depending on which modules are turned on. The schema does not change every release; it accretes slowly. Long-tenured analysts learn the data dictionary the way long-tenured clinicians learn anatomy.

## The relational model on a clinical surface

A relational database stores data in tables. Each table holds one kind of fact. Each row is one instance of that fact. Each column is one attribute. Tables are connected by *foreign keys*: a column in one table whose value is the primary key of a row in another table.

For Ms. Reyes's care, you can think of the operational EHR as carrying roughly these tables (the table names here are simplifications):

- `PATIENT`. One row per person. Holds demographics, identifiers, contact information.
- `ENCOUNTER`. One row per visit. Tied to a patient through `PAT_ID`. Holds visit type, department, primary provider, date.
- `PROBLEM_LIST`. One row per active or resolved problem on a patient's list. Tied to a patient through `PAT_ID` and (optionally) to the encounter where the problem was first surfaced.
- `MEDICATION_ORDER`. One row per medication order. Tied to a patient through `PAT_ID`. Holds the drug, the dose, the route, the frequency, the start and stop dates, the order status.
- `ALLERGY`. One row per documented allergy. Tied to a patient through `PAT_ID`.
- `LAB_RESULT`. One row per result component. Tied to a patient through `PAT_ID` and to the encounter through `PAT_ENC_CSN_ID`.
- `FLOWSHEET_VALUE`. One row per recorded measurement. Tied to a patient through `PAT_ID`, to the encounter through `PAT_ENC_CSN_ID`, and to the measurement type through a lookup table.
- `PROVIDER`. One row per clinician. Joined to encounters and orders.

When a clinician clicks **Medications** on Ms. Reyes's chart, the renderer asks the application server for "the active medication list for ER-001." The application server turns that question into a SQL query along the lines of:

```sql
SELECT m.MEDICATION_NAME, m.DOSE, m.DOSE_UNIT, m.ROUTE, m.FREQUENCY, m.START_DATE
FROM   MEDICATION_ORDER m
JOIN   PATIENT p ON m.PAT_ID = p.PAT_ID
WHERE  p.PAT_MRN_ID = 'ER-001'
  AND  m.ORDER_STATUS = 'Active'
ORDER BY m.START_DATE DESC;
```

Three rows come back. The renderer turns them into the three-line panel the clinician sees. That same pattern (query, join, filter, render) runs hundreds of times a minute across the institution.

A production query is more complicated than the one above, because in a real Epic Clarity database the medication order does not store its own drug name directly. It stores a code that points at a row in a `DRUG_MASTER` table; the drug master row points at an ingredient table; the ingredient table points at a route lookup and a frequency lookup. The renderer's question is one sentence; the database's answer involves six joins. The point is not the number of joins but the principle: **what you see as one screen is many tables stitched together by a query**.

## The flowsheet pattern: deliberate denormalization

Most of the EHR follows the relational model cleanly. Each kind of fact gets its own table with stable columns.

Then there is the flowsheet. Vitals, intake and output, pain scales, infusion-titration values, neurological checks, joint counts, ventilator settings, the ICU monitoring trace. Tens of thousands of distinct measurement kinds, captured at high frequency, configured locally by every department.

A strictly relational design would put each measurement kind in its own table or its own column. That cannot work. The cardinality of measurement kinds is too high, the rate of additions is too fast, and the operational team that configures new flowsheet rows is not the team that owns the database schema. So every EHR uses an **entity-attribute-value (EAV)** design for flowsheets:

| row | patient | encounter | measurement_name | value | recorded_time |
|---|---|---|---|---|---|
| 1 | ER-001 | ENC-300148 | Tender joint count | 2 | 2026-02-10 09:00 |
| 2 | ER-001 | ENC-300148 | Swollen joint count | 1 | 2026-02-10 09:00 |
| 3 | ER-001 | ENC-300148 | DAS28-CRP | 2.8 | 2026-02-10 09:00 |
| 4 | ER-001 | ENC-300148 | BP - Systolic | 122 | 2026-02-10 08:50 |
| 5 | ER-001 | ENC-300148 | BP - Diastolic | 76 | 2026-02-10 08:50 |

One table. One row per measurement instance. The schema does not change when clinical operations adds a new pain scale; only the contents of a `MEASUREMENT_NAME` lookup change. This is the *price* of clinical reality bumping into the relational model: most of the EHR is normalized cleanly, and flowsheets are deliberately not.

The trade-off:

- **Capture is flexible.** Adding a new measurement is a configuration change, not a schema change.
- **Storage is row-heavy.** A patient with an ICU stay produces tens of thousands of flowsheet rows where a relational design would have a few hundred.
- **Querying is hard.** Every analytic query has to pivot the EAV rows back into a wide table before doing anything useful.

The clinical data warehouse (Track 03) exists in significant part to pre-pivot the flowsheet data into shapes that analytics can use. The warehouse pays the flexibility cost at *write* time, in exchange for query convenience at *read* time. The operational EHR pays the convenience cost at read time, in exchange for flexibility at write time. Both designs are correct for their workload.

## Indexes and access patterns

Two queries against the same `MEDICATION_ORDER` table can take wildly different amounts of time depending on how the table is indexed.

An **index** is a separate data structure (commonly a B-tree) that lets the database find rows by a particular column without scanning every row. When the EHR is built, the database administrator chooses which columns to index based on which queries the operational system needs to be fast. The chart needs:

- Find all rows for this patient. Fast. Index on `PAT_ID`.
- Find all rows for this encounter. Fast. Index on `PAT_ENC_CSN_ID`.
- Find rows in a date range for this patient. Fast. Composite index on `(PAT_ID, START_DATE)`.

A research analyst asks "how many patients in our system are currently on adalimumab." That query filters `MEDICATION_ORDER` by `RXNORM_CODE = '327361'`. If there is no index on `RXNORM_CODE`, the database has to scan every row in the table to find the matching ones. On an 80-million-row production table, that scan can take minutes.

You might think: "fine, add an index on `RXNORM_CODE`." The reason the operational EHR will resist is that every additional index has a maintenance cost. When the chart writes a new medication order, the database has to update *every* index on the `MEDICATION_ORDER` table. The chart is doing this thousands of times a minute. Every extra index slows down inserts and updates. The operational system is sized for inserts; it stays fast because it does not maintain indexes it does not need.

This is the structural reason research and population queries are usually pointed at a separate analytics system (Track 03). The analytics system has different indexes, a different storage layout, and very different acceptable response times. It is sized for the workload analytics has, not for the workload the chart has.

## The physical view

Everything above is the *logical* picture. Below that is the *physical* picture, and most of an EHR's cost and resilience profile lives there.

### Block versus object storage

Two distinct storage primitives matter clinically:

- **Block storage.** Looks like a raw disk to the operating system. The storage volume is a long sequence of bytes; the OS can read or write any byte offset. Databases need this because they do small in-place updates: when the chart writes a new flowsheet row, the database is updating a single 8-kilobyte page in the middle of a 50-gigabyte data file. SAN, NAS, Amazon EBS, Azure Managed Disks, and Google Persistent Disk are block-storage architectures.
- **Object storage.** The unit is an entire object. Write once, read whole, never patch the middle. Objects are addressed by a long string key. Object storage scales to petabytes cheaply and is the default for archival and bulk-blob data. Amazon S3, Azure Blob Storage, Google Cloud Storage are the canonical cloud examples.

A typical clinical workload uses both:

- The operational EHR tables live on block storage, on the fastest tier the institution can afford.
- DICOM studies (Track 04), scanned documents, audio recordings, and most note PDFs live on object storage.
- Backups of the EHR database are written as object-storage blobs because they are immutable and large.
- The analytics data lake (Track 03) lives on object storage because it scales cheaply to terabytes and supports parallel reads.

### Hot, warm, cold: three media tiers

A 600-bed hospital cannot put its entire decade of PACS imaging on the fastest storage available. It cannot put the active EHR database on tape either. The answer is **tiering**:

| Tier | Media | Random-read latency | Cost per TB/year | Where it sits in the EHR |
|---|---|---|---|---|
| 1 (hot) | NVMe SSD | ~0.05 ms | $500 - $1,500 | Active EHR tables, recent encounters |
| 2 (warm) | SATA SSD or all-flash array | ~0.2 ms | $200 - $600 | Indexes, recent backups, recent PACS studies |
| 3 (cool) | 7,200 RPM HDD | ~5 ms | $30 - $80 | Older PACS, archived records, secondary backups |
| 4 (cold) | LTO tape or cold-archive object | seconds to hours | $3 - $10 | Long-term archives, regulatory retention, DR copies |

Movement between tiers is handled by **hierarchical storage management (HSM)**: an automated process that promotes hot data to fast tiers and demotes cold data to cheap tiers based on age, access pattern, and policy.

The clinical decisions wrapped inside the tiering policy:

- When a patient comes back for a follow-up after several years, where is their old imaging? If the comparison study is on a cold tier with a multi-hour rehydration time, the visit cannot use it.
- When the EHR database is destroyed and has to be restored from backup, the restore time is bottlenecked by the bandwidth between the backup tier and the recovery target. A 10 TB database from cold-archive object storage can take many hours to come back.

These are clinical and operational questions disguised as IT decisions. Informaticists belong in the conversations that set the policies.

### On-prem, cloud, hybrid

Twenty years ago every hospital ran its EHR on servers in its own basement. Today the deployment landscape is mixed:

- **On-prem.** Hospital owns the hardware, runs it in a hospital data center. Full control over the physical environment. All compliance work happens inside the hospital's HIPAA-covered boundary. Costs are capital-heavy and largely fixed.
- **Cloud.** Workloads run in a hyperscaler's data center. The hyperscaler signs a Business Associate Agreement (BAA) with the hospital and operates within HIPAA scope for the services covered. Costs become operational expense, scaling with workload. Both Epic and Oracle Health offer hosted options now.
- **Hybrid.** The most common production reality. Operational EHR on-prem; backups, PACS archives, analytics workloads, AI training pipelines, and DR copies in the cloud.

The boundary between on-prem and cloud is where most of the HIPAA work lives. Every data path that crosses the boundary needs encryption in transit, the cloud destination needs encryption at rest, and the BAA needs to cover every service touched by the data.

### Backup, replication, and disaster recovery

Three terms that are easy to confuse and matter enormously when the EHR is down:

- **Backup.** A point-in-time copy of the database, stored separately, intended to be restored if the live database is corrupted or destroyed.
- **Replication.** A continuously updated mirror of the live database on a second server or a second site. Replicas keep the EHR available during a failure by cutting traffic over to the mirror.
- **Disaster recovery.** The plan for what the hospital does when the entire primary site is unavailable. Documented runbooks, tested cutover procedures, agreed objectives.

Two metrics any informaticist should be able to ask about:

- **RPO (recovery point objective).** The maximum amount of data the hospital is willing to lose if a disaster strikes. RPO of 5 minutes means transaction logs ship every 5 minutes.
- **RTO (recovery time objective).** The maximum amount of time the hospital is willing to be without the EHR. RTO of 30 minutes means cutover must complete in 30 minutes.

Both numbers cost money, and both are clinical and operational decisions disguised as IT decisions.

## The compromise the operational EHR makes

If you step back, the design of the operational EHR is shaped by a single overriding constraint: **it has to be fast and reliable for the chart, all day, every day**. Every decision in the schema, in the indexing, in the physical layout, in the backup posture, is downstream of that constraint.

This means the operational EHR is structurally bad at population queries. It is bad at long-running analytical work. It is bad at lossless data export. It is bad at sharing data with anyone outside the hospital.

The three together give you a vocabulary for placing any clinical data flow on the operational-versus-analytical axis.
