## Why this track has a "before" in its name

Most introductions to FHIR start with a resource (Patient, Observation, MedicationRequest). That works for readers who already have the underlying intuitions about data shapes, the web, and the history that produced the standard. This track puts those intuitions in place first: how data is shaped, how the web moves it, how healthcare got from paper to here, and what "interoperability" means the moment you try to make two systems talk.

Once those four ideas are in place, the FHIR resource model is the obvious answer to the question. Four ideas come first.

---

## 1. Data has three shapes

"The patient's data" can mean three different things. The difference is load-bearing.

### Spreadsheet shape

One fact per cell, every row the same columns. A flowsheet is a spreadsheet. A lab report exported to CSV is a spreadsheet. A registry extract on someone's desktop is a spreadsheet.

Ms. Reyes's CRP values over four years, written out as `date, value, units, lab`, is a spreadsheet. Every row has the same five columns. You can sort by date, average across rows, plot against time, and hand it to anyone with a CSV reader.

Spreadsheets work well for homogeneous rows of one kind of fact. They fail when you want to attach a different kind of fact to one of those rows ("this CRP was drawn at the same visit as a swollen joint count of three and a patient global of forty"). The row then needs context the spreadsheet model can't carry cleanly.

### Database shape

Several tables, each holding a different kind of row, linked by stable identifiers. A `patients` table with one row per patient. An `encounters` table with one row per visit, each row pointing at a patient. A `labs` table with one row per result, each row pointing at an encounter. An `orders` table, a `medications` table, a `notes` table, all linked.

OMOP (covered in Course 07) is one specific shape of database. The vendor schemas inside Epic and Cerner are other database shapes. EHRs are databases under the hood; the UI you click is a view that runs joins on your behalf.

Databases work well for heterogeneous related facts. They fail when you try to move the data out without a lossy export, because the relationships across many tables do not survive being flattened.

### Document shape

A single self-contained record with internal structure. A FHIR Bundle is a document. A discharge summary in a CDA file is a document. A patient handout printed at the end of a visit is a document.

A document carries everything it needs in one piece. Ms. Reyes's FHIR Bundle holds her demographics, her problems, her current medications, her recent labs, and the references between them, all in one JSON object. Another system receives the whole story without needing access to your database.

Documents work well for moving data across system boundaries. They are not where you do bulk analytics; for that you flatten them back out into spreadsheet or database shapes.

### Why the shape matters

Every healthcare data interaction is a translation between shapes. A FHIR Bundle (document) gets ingested into a clinical data warehouse (database), which gets exported to a research extract (spreadsheet), which gets joined back to a registry feed (database), which gets serialized into a FHIR Bundle (document) for return.

You can lose information at every step. Knowing which shape you're in tells you what kinds of loss to look for.

FHIR is a document shape on the wire (resources, bundles, JSON) backed by a database shape conceptually (resources reference each other by stable IDs). Both halves matter. The wire shape moves data; the conceptual shape keeps it consistent.

## 2. Three web ideas underneath FHIR

The web is a small number of agreements layered on top of each other. Three of them matter for FHIR.

### HTTP: request and response

A client (a browser, a phone, a FHIR app) sends a request to a server. The server sends back a response. Each request and response has a small set of named parts: a method (what you want to do), an address (what you want to do it to), some headers (metadata about the request or response), and optionally a body (the content).

The restaurant analogy. You walk into a restaurant and say "I'd like the salmon." That is a request. It has an implicit method (I want to receive), an address (the salmon, which is on the menu), and a body (none for ordering, but eventually the salmon arrives, which is the response body). The waiter walks back ten minutes later with a plate. That is a response. Sometimes the response is "we're out of salmon," which is the server returning a status code that says "what you asked for doesn't exist right now."

HTTP has a small set of methods that matter for FHIR:

- `GET`: read something. Idempotent, cacheable, never modifies state. "Bring me the salmon."
- `POST`: create something new. "Please add an order for salmon."
- `PUT`: replace something that already exists at a known address. "Replace the order at table 4 with this one."
- `DELETE`: remove something. "Cancel the order at table 4."

And a small set of status codes that matter:

- `200 OK`: I did what you asked.
- `201 Created`: I did what you asked, and a new thing now exists.
- `404 Not Found`: I don't know what you're asking about.
- `401 Unauthorized` / `403 Forbidden`: you can't ask me that, either because you didn't prove who you are or because I won't let you.
- `500 Internal Server Error`: something broke on my end.

That's most of HTTP for FHIR purposes.

### REST: every thing has a stable address

REST is an architectural idea, not a specification. Its central claim: the things in your system are *resources*, each resource has a *stable address*, and the actions on a resource are the HTTP verbs.

In a RESTful API, you don't have endpoints like `/getPatientById?id=42`. You have an address `/Patient/42`, and you `GET` it, `PUT` to it, or `DELETE` it. The address names the thing; the verb names the action. Adding a new kind of thing means adding a new address pattern, not a new function for every action.

REST is why FHIR URLs look the way they do. Querying for Ms. Reyes's most recent CRP is something like:

```
GET https://hapi.fhir.org/baseR4/Observation?subject=Patient/ER-001&code=1988-5&_sort=-date&_count=1
```

The address (`Observation`) names the kind of thing. The query parameters (`subject`, `code`, `_sort`, `_count`) narrow it down. The verb (`GET`) says you want to read. Course Track 2 builds queries like this.

### JSON: a way of writing structured data down

JSON (JavaScript Object Notation) is a format for serializing structured data. It looks like this:

```json
{
  "resourceType": "Patient",
  "id": "ER-001",
  "name": [{"family": "Reyes", "given": ["Elena", "Maria"]}],
  "birthDate": "1974-02-09"
}
```

Curly braces wrap an object. Each entry is a key (in quotes) followed by a value. Values can be strings, numbers, booleans, null, lists (in square brackets), or other objects. Lists of objects look like `[{...}, {...}]`. That is the entire format.

JSON has two properties that matter for FHIR. First, every mainstream programming language has a built-in JSON parser, so receiving JSON does not impose tooling on the recipient. Second, JSON is human-readable. You can open a FHIR resource in a text editor and follow what it says, slowly, the same way you would follow a written paragraph. CDA, which uses XML, is also human-readable in principle; in practice the verbosity makes it unfriendly. JSON's compactness was a deliberate choice.

FHIR resources can also be expressed in XML and (later) in RDF. JSON is the default because the modern web defaulted to it.

## 3. How healthcare got here

It is tempting to tell this story as if FHIR is the answer and everything before was a mistake. That is wrong, and it sounds wrong to anyone who has worked in a hospital that still runs on the previous standards.

Each major health-data standard solved a real problem with the tools available at the time. None have been retired. They layer.

### HL7 v2 (1989)

The problem: getting a lab result from the lab system into the order entry system, so the ordering clinician sees the value next to their order. In 1989 there was no widespread web. The networks that hospital systems shared were ad hoc, often serial, and slow. The data had to be small and fast.

HL7 v2 is a pipe-delimited message format. A message looks like:

```
MSH|^~\&|LAB|HOSP|EHR|HOSP|202405161145||ORU^R01|MSG00001|P|2.5.1
PID|||ER-001||REYES^ELENA||19740209|F
OBR|1|||1988-5^C reactive protein
OBX|1|NM|1988-5^C reactive protein||36.2|mg/L|0-5|H
```

Pipes separate fields, carets separate components, and the first three characters of each line name the segment. The format is opaque on first encounter and very useful once you know it. HL7 v2 is still the dominant standard for moving structured data between systems inside a hospital. Every major EHR speaks it. If your lab system talks to your EHR right now, it is almost certainly speaking v2.

HL7 v2 fit its problem (small, fast, point-to-point messages inside a hospital). It did not fit sharing whole clinical documents across organizations, because its segments were too tightly bound to specific message types.

### CDA (2005)

The problem: sharing a complete clinical document, like a discharge summary, between two organizations that don't share an EHR. The receiver should be able to display the document as a human-readable narrative and also extract the structured pieces (medications, problems, allergies) into their own system.

CDA (Clinical Document Architecture) is an XML format for clinical documents. A CDA document is a single XML file that contains a human-readable narrative section and machine-readable structured sections. The structured sections use templates that constrain what goes where: a "medications section" looks the same in every CDA document because the template said so.

CDA solved the problem it was built for. CCDs (Consolidated CDA documents) are still the format underneath most Direct messaging traffic between organizations, and they still flow under Meaningful Use exchange. CDA did not fit fine-grained queries, because the document is the unit of exchange. You cannot ask CDA "give me this patient's last five CRPs." You can only ask for "a document" and then parse out the CRPs you wanted.

### FHIR (2014, R4 stable in 2019)

The problem: building applications that read and write clinical data the way modern web applications read and write everything else. Previous standards required specialized tooling and did not match what a web developer already knew. The talent pool was small and aging.

FHIR (Fast Healthcare Interoperability Resources) is a set of resources (Patient, Observation, MedicationRequest, Condition, and so on) addressable via a RESTful API, serializable in JSON or XML, and assembled into Bundles when you need a whole record. It reuses the web's existing tools (HTTP, REST, JSON, OAuth) rather than inventing new ones. A developer who knows how to build a Twitter client can read a FHIR record on day one.

FHIR did not replace HL7 v2. The lab still sends results to the EHR via v2 in most hospitals; if FHIR carries that traffic in your hospital, it is a recent change. FHIR also did not replace CDA: Direct messaging between organizations still uses CCDs in many networks. What FHIR added was a layer where new applications could read and write clinical data the way the modern web does. That layer is where CDS Hooks, SMART on FHIR apps, and the recent ONC/CMS interoperability rules live.

The three layers coexist. HL7 v2 is the messaging layer inside a hospital. CDA is the document layer between organizations. FHIR is the API layer for new applications.

## 4. Paper chart, EHR, FHIR

A continuity story in three steps.

**Paper chart.** Structured by physical layout (the H&P on one form, the progress note on another, the lab slip pasted into the labs section). Single site (one chart per institution). Single author per page. Queryable only by reading. Movable only by photocopying and mailing. The structure was in *the paper itself*: a labs section was where the labs were because someone clipped them there.

**EHR.** Structured by vendor schema (Epic's tables differ from Cerner's, which differ from MEDITECH's). Single site per vendor instance (your Epic does not talk to the Epic across town without effort, and your Epic certainly does not talk to the Cerner across town). Multi-author with audit trail. Queryable inside the vendor's tools. Movable only with custom integration. The structure is in *the database schema*, and the schema is the vendor's intellectual property.

**FHIR.** Structured by a shared specification (an Observation looks the same regardless of which vendor produced it). Multi-site by design (resource IDs are URLs, the API is RESTful). Multi-author with provenance built into the resources. Queryable by anyone with HTTP. Movable by definition. The structure is in *the specification*, which is public, free, and the same for everyone.

Each step kept what was useful from the previous one and added a new layer. The paper chart is still the right shape for a bedside chart-flip in some long-term care and resource-limited settings. The EHR is still the right shape for in-system documentation, where the speed and integration of vendor tooling matters more than portability. FHIR is the right shape for the boundary: moving data from one system to another, building third-party apps, sending data out for research.

FHIR is not the end state. It is the current state of the boundary layer.

## 5. Where interoperability actually breaks

"Interoperability" gets used as if it is one thing. It is at least five things layered on top of each other. When two systems "can't talk," the question is *at which layer*. Most interop arguments stall because no one has named the layer.

1. **Transport.** Can the two systems even reach each other on a network? Right firewall rules, right TLS, right authentication. A `404` or a connection timeout lives here. Usually a problem the IT department owns.
2. **Format.** Are the two systems speaking the same format? JSON vs XML vs HL7 v2 pipes. A parser failure on one side lives here.
3. **Structure.** Are the same facts in the same places? Epic puts a patient's MRN at `PAT_ENC.PAT_MRN_ID`. Cerner puts it inside an array at `person_alias[].alias`. Both are valid JSON. Both contain the MRN. Neither is what the other system expects. A field-mapping spreadsheet lives here.
4. **Terminology.** Are the codes the same? Epic codes the diagnosis as ICD-10 `M05.79`. Cerner codes the same diagnosis as SNOMED CT `239791008`. Both are correct in their own vocabularies. Translating between them requires a value set map. A "the receiving system says this code doesn't exist" lives here.
5. **Content.** Did the sender even capture what the receiver expects? If Epic stored the anti-CCP result and Cerner didn't capture it at all, no amount of mapping fixes that. The data isn't there to map. A workflow change at the sender lives here.

FHIR (and US Core, mCODE, and the implementation guides covered in later tracks) addresses layers 2, 3, and partially 4. Layer 1 is the network team's job. Layer 5 is a workflow problem that no standard can solve by itself.

The capstone in the notebook walks four real differences between Ms. Reyes's Epic and Cerner exports and asks you to classify each one. By the end you can say, of any "the system can't read our data" complaint, which layer the problem lives at. That specificity unblocks most interop conversations.

## What to do with this

As you read the rest of the FHIR course, hold these four ideas in mind:

- **Data has three shapes.** FHIR is document-shaped on the wire and database-shaped conceptually. When you query or post FHIR, you are moving documents that point at each other.
- **Three web ideas sit underneath FHIR.** HTTP verbs, REST resources, JSON serialization. FHIR adds nothing exotic on top of these. The exotic part is the shared specification for the resources themselves.
- **The history layers.** HL7 v2 is still everywhere. CDA is still everywhere. FHIR is the new boundary layer. Knowing which one carries which traffic is most of the answer to "how does data move in this hospital."
- **The five interop layers.** Transport, format, structure, terminology, content. Most interop arguments are really arguments about which of these is broken.

Track 1 picks up from here and introduces resources, references, bundles, and the terminology systems FHIR uses (LOINC, SNOMED CT, RxNorm). The vocabulary moves fast; the structure underneath is what this track put in place.
