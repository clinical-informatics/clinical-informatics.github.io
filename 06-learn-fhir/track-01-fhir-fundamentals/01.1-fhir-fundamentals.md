## Why "read and navigate" comes before "write"

A FHIR bundle is a record. The first useful thing to do with a record is read it, the same way the first useful thing to do with a discharge summary from another facility is read it before writing your own consult note. Authoring valid FHIR (the work of Track 3) requires an opinion about what the right resource looks like, and you only have that opinion after reading enough.

This track is the reading part. The track closes with the reader able to open an unfamiliar FHIR bundle, identify which resources are in it, follow the references that connect them, and pull a clinically coherent picture out the other side. That picture is what the capstone asks you to write.

Four ideas come before the capstone: what a resource is, how references work, what a bundle is, and which terminology system to expect in which coded slot. Plus a short concept-level introduction to search parameters, because they will be how you ask a FHIR server questions in Track 2.

## 1. A resource is a unit of clinical data

A FHIR **resource** is one piece of clinical information shaped according to a published specification. Patient is a resource type. Observation is a resource type. MedicationStatement is a resource type. Condition is a resource type. There are about 150 resource types in FHIR R4. Day to day, most clinical workflows touch roughly twenty of them.

A resource has three things:

- **A `resourceType`.** Names what kind of clinical fact it is.
- **An `id`.** A stable identifier within the system that holds it.
- **A set of fields specific to that type.** A Patient has `name`, `gender`, `birthDate`, `address`. An Observation has `code`, `value`, `effectiveDateTime`, `subject`. A MedicationStatement has `medicationCodeableConcept`, `status`, `effectivePeriod`, `dosage`.

Here is Ms. Reyes's Patient resource, slightly trimmed:

```json
{
  "resourceType": "Patient",
  "id": "elena-reyes",
  "identifier": [{
    "use": "usual",
    "type": {"coding": [{"system": "http://terminology.hl7.org/CodeSystem/v2-0203", "code": "MR"}]},
    "system": "http://clinical-informatics.example/mrn",
    "value": "ER-001"
  }],
  "active": true,
  "name": [{"use": "official", "family": "Reyes", "given": ["Elena", "Maria"]}],
  "gender": "female",
  "birthDate": "1974-02-09",
  "address": [{"use": "home", "line": ["742 Elm Street"], "city": "Springfield", "state": "MA", "postalCode": "01103"}],
  "communication": [
    {"language": {"coding": [{"system": "urn:ietf:bcp:47", "code": "en-US"}]}, "preferred": true},
    {"language": {"coding": [{"system": "urn:ietf:bcp:47", "code": "es"}]}}
  ]
}
```

Read it once. Every Patient resource anywhere in the world that speaks FHIR R4 takes the same shape. That is the entire point.

Two patterns to flag. First, every place that holds an identifier or a code value uses an array of objects, not a bare string. Even when there is "only one" name, the `name` field is an array containing one object. The array is the structure FHIR uses uniformly so that resources can grow to multiple values without changing shape (a patient might have a maiden name and a current name; a problem might have multiple codings in different vocabularies). Second, almost every value goes inside a wrapper object that names its system. A language is not the string `"en-US"`. It is an object containing a `coding` array, each entry of which has a `system` and a `code`. The wrapper makes the value unambiguous across vocabularies. The next section returns to this.

## 2. References connect resources

A resource that is *about* another resource says so with a **Reference**. A Reference is a small object containing a `reference` field that names the resource being pointed at.

Ms. Reyes's CRP observation says it is about Ms. Reyes:

```json
"subject": { "reference": "urn:uuid:patient-elena-reyes" }
```

References come in three flavors. The flavor depends on where the resource is and who is reading it.

- **Relative reference.** `Patient/elena-reyes`. The most common form in practice. It means "the Patient resource with id `elena-reyes` on the same FHIR server that gave you this resource." Cheap, common, what a FHIR server returns when you query it.

- **Absolute URL.** `https://hapi.fhir.org/baseR4/Patient/elena-reyes`. The full address of the resource somewhere on the web. Used when the resource lives on a different server than the one you're reading from.

- **`urn:uuid:` reference.** What Ms. Reyes's bundle uses. The reference is a UUID that matches the `fullUrl` of another entry in the same bundle. UUIDs are used when the bundle is a self-contained snapshot whose resources do not yet have permanent server URLs. The resources still point at each other; the addresses are temporary names that live only inside this bundle.

All three say the same thing: "I am about that resource over there." A receiver reading any of them follows the pointer to the resource being named.

Most of the work of understanding a clinical fact in FHIR is following references. The Observation has a CRP value, but it points at the Patient who had it drawn and at the Encounter where it was drawn. The MedicationStatement has a dosage, but it points at the Patient taking the medication and (often) at the Condition the medication is for. Reading a FHIR record is following these pointers and assembling the parts.

## 3. A bundle is a container of resources

A **Bundle** is a single envelope that holds multiple resources. Three kinds of bundle matter for this course.

- **Collection.** Bundle `type` is `collection`. A snapshot of resources packaged together with no inherent semantic beyond "here are these resources together." Ms. Reyes's bundle is a collection. The references between resources inside a collection bundle are typically `urn:uuid:` references that name other entries in the same bundle.

- **Transaction.** Bundle `type` is `transaction` (or `batch`, which is similar). A set of operations the receiver is supposed to apply, atomically (for transaction) or sequentially (for batch). Each entry specifies a method (`POST`, `PUT`, `DELETE`) and a URL. Used to send "here are several resources to create or update, all at once." You will see these in Track 3 when you write FHIR.

- **Searchset.** Bundle `type` is `searchset`. What a FHIR server returns when you run a search query. The entries are the resources matching your search, with paging information at the top of the bundle (total count, next-page link). You will meet this in Track 2.

All three have the same shape: a top-level `Bundle` object with a `type`, and an `entry` array. Each entry holds one resource (in `entry[].resource`). The difference is what the array *means*: a snapshot, a set of operations, or a search result.

The bundle is FHIR's primary unit of exchange. You rarely send or receive a single bare resource. Almost always you send or receive a bundle, even if it contains only one resource. That detail will save you from confusion when you start working with real responses.

## 4. Terminology goes in the slots

Almost every clinical fact in FHIR involves a code. The diagnosis on a Condition is a code. The test on an Observation is a code. The drug on a MedicationStatement is a code. The unit on a quantity is a code. The criticality of an allergy is a code. The status of a resource is a code.

FHIR does not define its own clinical vocabulary. It reuses the existing standard vocabularies and specifies which one belongs in which slot.

| Slot | Vocabulary | URI in practice as `system` |
|---|---|---|
| Lab tests, panels, vital sign codes | **LOINC** | `http://loinc.org` |
| Clinical findings, procedures, problems | **SNOMED CT** | `http://snomed.info/sct` |
| Medications | **RxNorm** | `http://www.nlm.nih.gov/research/umls/rxnorm` |
| Units of measure (quantities) | **UCUM** | `http://unitsofmeasure.org` |
| ICD-10 codes (billing-aligned diagnoses) | **ICD-10-CM** | `http://hl7.org/fhir/sid/icd-10-cm` |
| CPT codes (procedures, billing-aligned) | **CPT** | `http://www.ama-assn.org/go/cpt` |
| Vaccines | **CVX** | `http://hl7.org/fhir/sid/cvx` |
| Languages | **BCP-47** | `urn:ietf:bcp:47` |
| Race / ethnicity (US Core) | **CDC race & ethnicity** | `urn:oid:2.16.840.1.113883.6.238` |
| Resource statuses and other admin concepts | **HL7 / FHIR-defined CodeSystems** | various `http://terminology.hl7.org/...` and `http://hl7.org/fhir/...` URIs |
| Site-specific identifiers (MRN systems, etc.) | **Local** | URIs the local site defines |

The pattern is the same in every coded slot: a `coding` array, each entry a `{system, code, display}` triple. The `system` URI names the vocabulary. The `code` is the value in that vocabulary. The `display` is a human-readable string, supplied for convenience but never trusted as the canonical meaning. The canonical meaning is the `system` + `code` pair.

A coded slot can carry multiple codings at once. A Condition's `code.coding` array can hold both an ICD-10 entry (for billing) and a SNOMED CT entry (for clinical findings), both referring to the same concept. FHIR handles the layering of vocabularies most healthcare systems live with by this mechanism: do not pick one, send both, let the receiver pick which to use.

## 5. Search parameters at a concept level

Reading a resource you already have is one thing. Asking a server for resources you don't yet have is another. The way you ask is via a **search**: a `GET` request to a resource type's URL, with query parameters that narrow the result.

The shape of a search:

```
GET /Observation?subject=Patient/elena-reyes&code=1988-5&_sort=-date&_count=1
```

Each parameter is defined by the FHIR spec. The ones you will meet most:

- **`subject` (or `patient`).** Narrow to a specific patient.
- **`code`.** Narrow to a specific clinical code. Often paired with a system: `code=http://loinc.org|1988-5`.
- **`date`, `effective-date`, `onset-date`.** Narrow to a time window. Comparators like `gt`, `lt`, `ge`, `le` are supported: `date=ge2024-01-01`.
- **`status`.** Resources with a particular status: `status=active`.
- **`_sort`.** Sort the results. Prefix with `-` for descending. `_sort=-date`.
- **`_count`.** Maximum number of results per page. `_count=20`.
- **`_include` and `_revinclude`.** Pull along referenced resources or resources that reference the result. `_include=Observation:patient` returns the Observation plus the Patient it points at, in one response.

Every resource type has its own defined search parameters. The Observation resource defines about thirty; the Patient resource about twenty; the MedicationStatement about fifteen. The full list per resource type is in the FHIR R4 spec.

For Track 1 you do not need to memorize any of this. The concept worth carrying is that searches are uniform across resource types: same `GET` verb, same URL shape, same parameter style. Track 2 has you write real queries against hapi.fhir.org and see exactly what comes back.

## How to read any unfamiliar FHIR resource

For any resource you have never seen before, three questions handle most of the work.

1. **What is the `resourceType`?** That tells you which fields will be present. The FHIR spec page for that type lists them. Most resource pages are short enough to skim in two minutes.
2. **Who does it belong to?** Almost every clinical resource has a `subject` (or `patient`) reference pointing at a Patient. Follow it. The resource only makes clinical sense in the context of the patient it belongs to.
3. **What are the load-bearing fields?** The code (what is this resource *about*?), the value or status (what does it say?), the effective time (when?), and any references to related resources (encounter, recorder, reason). Most clinical questions are answered from these four.

Answer those three questions and you can read any FHIR resource. The notebook applies exactly that procedure to Ms. Reyes's bundle.

## What to do with this

As the rest of the course (Tracks 2 through 5) moves quickly, hold onto these four ideas:

- **A resource is a unit of clinical data with a type, an id, and the fields its type defines.** Read the type first; the fields follow from the type.
- **References are how resources connect.** Follow them to reconstruct a patient's record from the parts.
- **A bundle is a container; the type of bundle tells you what the container means.** Collection (snapshot), transaction (operations to apply), searchset (server response to a search).
- **Codes live in `system`+`code` pairs, and the vocabulary belongs to the slot.** LOINC for labs, SNOMED for findings, RxNorm for medications, UCUM for units, ICD-10 for billing-aligned diagnoses.

Track 2 introduces talking to a FHIR server with these patterns. Track 3 introduces writing them.
