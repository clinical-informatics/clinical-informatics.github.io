## What an implementation guide actually is

A FHIR **implementation guide** (IG) is a package that says, for a specific use case, "here is exactly what FHIR resources should look like in this context." It bundles together:

- **Profiles** (StructureDefinition resources) that constrain base FHIR resources for the use case.
- **Extensions** (also StructureDefinition resources) for data the base spec does not have.
- **Value sets and code systems** that constrain which codes can go in which slots.
- **CapabilityStatements** that describe what conforming servers must support.
- **Examples** of conforming resources.
- **Narrative documentation** that explains the why behind each constraint.

An IG is **versioned and published**. US Core 6.1 is a specific snapshot of the US Core IG. mCODE 3.0 is a specific snapshot of mCODE. Conforming systems claim conformance to a specific version, not "US Core" in general.

The IGs you will meet most:

- **US Core** (hl7.org/fhir/us/core). The base IG for US clinical FHIR exchange. The CMS / ONC interoperability rules require certified health IT to support US Core.
- **mCODE** (hl7.org/fhir/us/mcode). Minimal Common Oncology Data Elements. Profiles for cancer-relevant data: cancer condition, staging, genetic findings, treatments.
- **IPS** (hl7.org/fhir/uv/ips). International Patient Summary. The international cousin of US Core, designed for cross-border summary exchange.
- **CARIN BB** (hl7.org/fhir/us/carin-bb). Patient access to claims data. The IG behind the CMS Blue Button 2.0 work.
- **DaVinci** family (hl7.org/fhir/us/davinci-pdex and family). Payer-provider data exchange, prior authorization, formulary lookup.
- **SDOH-CC** (hl7.org/fhir/us/sdoh-clinicalcare). Social determinants of health.

Each IG addresses a specific clinical or operational use case. Most production deployments conform to a handful of IGs at once, layered: US Core for the base patient summary, mCODE for the cancer-specific data, DaVinci for the payer interactions, and so on.

## Anatomy of an IG

Open any published IG website (US Core or mCODE are good starting points) and you will see a similar structure.

- **Home / Spec / Profiles.** The list of StructureDefinitions in the IG. Each profile has its own page describing what it constrains.
- **Extensions.** A list of extensions the IG defines or relies on.
- **Value Sets / Code Systems.** The terminology bindings.
- **Examples.** Conforming resources you can read and reuse.
- **Conformance.** A CapabilityStatement plus a list of which profiles a conforming server must support.
- **Downloads.** The IG packaged as a `.tgz` file you can feed to validators and IDEs.

When you look at a profile's page, four sections matter most.

- **Differential.** What the profile changed relative to its parent. Short. This is what the IG author actually wrote.
- **Snapshot.** The full element list expanded against the base spec. Long. Computed from the differential.
- **Constraints.** Invariants the profile adds beyond cardinality (e.g., "if `effectivePeriod` is present, both `start` and `end` must be present").
- **Must-Support.** The list of elements marked as must-support, alongside narrative explaining what "support" means for each one.

For everyday reading, start with the **differential**. It is the small, human-readable description of what the IG author cares about. Read the snapshot only when you need to know the full element shape (often when generating code).

## Profiles inherit, the way classes do

A profile has a `baseDefinition` field that names what it constrains. US Core Patient's `baseDefinition` is the base FHIR Patient. US Core Observation Lab's `baseDefinition` is US Core Observation Clinical Result (a *parent* US Core profile). mCODE Primary Cancer Condition's `baseDefinition` is US Core Condition Problems and Health Concerns, which in turn extends the base Condition.

That gives you a chain:

```
mCODE Primary Cancer Condition
    ↳ US Core Condition Problems and Health Concerns
        ↳ FHIR R4 Condition
```

When a system claims conformance to mCODE Primary Cancer Condition, it is implicitly conforming to US Core Condition (because mCODE extends it) and to base Condition (which US Core extends). Constraints accumulate down the chain. The differential at each level only describes what *that* level adds.

This is how the conformance landscape gets complicated. A single Condition resource might need to satisfy base Condition, US Core Condition Problems and Health Concerns, mCODE Primary Cancer Condition, and a state-specific cancer registry profile from a public-health IG. Each one adds constraints, and the resource has to satisfy the union.

## Must-support, revisited carefully

Track 3 introduced must-support as a contract on the receiver, not the sender. Track 4 adds the realistic complication: **what "support" means depends on the IG author's interpretation, and IGs disagree.**

Some IGs publish detailed narrative for each must-support element. US Core does this well: every must-support element has a paragraph or two saying exactly what support involves (display the data, store the data, support the relevant search parameter, gracefully handle absence, etc.).

Some IGs publish only the must-support flag without elaboration. The reader has to guess.

This is the "ambiguous must-support" footgun, and it is the source of most claimed-conformance disputes. Two vendors both claim to support US Core Observation Lab. One silently drops the `interpretation` field on display because they consider "support" satisfied by storage; the other considers display required. Both can defensibly claim conformance under a loose reading. A clinical informaticist evaluating either vendor has to ask, for each must-support element, "what does *your* implementation actually do with this?"

A useful checklist when reading an IG's must-support list:

1. Does the IG narrative define support for this element? If not, treat it as ambiguous.
2. Is "support" expected to include display, or only storage?
3. Is support expected to round-trip (the data survives a read-write-read cycle without loss)?
4. Is support expected to include the relevant search parameter being implemented?
5. What happens if the field is absent? Is `dataAbsentReason` required?

The answers determine whether two systems claiming conformance to the same IG actually interoperate.

## Portability vs interoperability, defined

These two words get used interchangeably and they should not be.

- **Portability.** I can move my data to another system. The data travels intact. The receiving system does not necessarily have to know how to *interpret* it, only how to store it.
- **Interoperability.** My data works in your system without either of us changing anything. The receiving system reads, displays, computes on, and reasons about the data with full fidelity.

OMOP (course 07) is a portability format. The standard is the table schema; the receiver loads the data into their own OMOP instance and can run OHDSI tools against it. They do not need to understand the source EHR's schema; they need to receive OMOP.

FHIR aims at interoperability. The standard is not only the wire format but also the semantics: this is a CRP, this LOINC code, this UCUM unit, this reference range. The receiver does not only store the value; they know what it *means* and can do clinical work with it.

Most real systems need both. Portability tells you how your data exits a system; interoperability tells you whether the next system can read it. An IG like US Core sits squarely on the interoperability side: it specifies not only the shape of the resource but also the value sets, the must-support semantics, and the conformance expectations.

The shorthand that helps: portability is one-way (out of your system); interoperability is two-way (between any two systems that speak the same IG).

## Gap analysis: what an IG does not cover

For any specific clinical use case, a published IG usually covers some of what you need and not others. The work of a clinical informaticist evaluating an IG is a gap analysis: list the data your workflow needs, line up the IG's coverage against your list, and document the gaps.

The notebook's capstone walks one such gap analysis for rheumatology against US Core. The structured rows ask, for each US Core Observation Lab must-support element, whether it covers what an RA monitoring workflow needs, then asks the inverse: what RA-specific data does an RA workflow need that US Core does not capture?

The answer for rheumatology: US Core covers the labs reasonably well; it does not cover composite scores, joint-count assessments, treat-to-target adherence, or biologic-line tracking. Those four gaps could be closed by an "RA Monitoring IG" layered on top of US Core, defining:

- A profile for DAS28 (or its sub-scores) as Observations with structured components.
- A profile for joint-count assessments (TJC, SJC) as Observations.
- An extension on Condition or MedicationStatement for "treat-to-target target" and "current line of therapy."
- A profile for biologic medications with the line number, prior failures, and effective period clearly captured.

There is no real "RA Monitoring IG" today (as of the curriculum's writing). If you wanted to publish one, the tooling is the same as for any HL7 IG: write the StructureDefinitions in FHIR Shorthand (FSH), use SUSHI to compile, publish via the HL7 IG publisher.

## What to carry into Track 5

Track 5 introduces SMART on FHIR, which is itself an implementation guide (the SMART App Launch IG). It defines profiles for OAuth scopes, authentication flow, launch context, and the CapabilityStatement extensions a SMART-enabled server has to expose. Reading the SMART IG with this track's vocabulary in place (StructureDefinitions, must-support, capability statements, conformance) is what makes SMART feel ordinary instead of magical. It is another IG layered on top of US Core.
