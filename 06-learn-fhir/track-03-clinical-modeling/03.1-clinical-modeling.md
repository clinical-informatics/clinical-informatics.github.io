## What changes when you go from reading to writing

Track 1 had you reading bundles. Track 2 had you reading server responses. Track 3 asks the inverse question: when you sit down to *write* a FHIR resource from scratch, what has to be in it?

The wire format is the same. A FHIR resource is a JSON object with a `resourceType`, an `id` (sometimes), and a set of fields appropriate to that type. The difference is responsibility. As a reader, you trust whatever the sender wrote. As a writer, you are the sender, and a downstream system will reject your resource if it is malformed. This track teaches what "malformed" means and how to find out before something breaks.

Four ideas come first: the minimum required fields per resource type, profiles as constrained versions of those resources, the must-support contract, and the `$validate` endpoint that lets a server tell you what is wrong.

---

## 1. The minimum required fields

Every FHIR resource has a published spec page (for Observation, that's `hl7.org/fhir/R4/observation.html`). The spec lists every field, its cardinality (`0..1`, `1..1`, `0..*`, `1..*`), and its data type. Fields with a minimum cardinality of 1 are required. Everything else is optional.

For the four resource types you will author in this track, the minimum requirements are small.

### Observation (the lab result, vital sign, exam finding)

| Field | Required? | Notes |
|---|---|---|
| `resourceType` | yes | Always `"Observation"`. |
| `status` | yes (1..1) | One of `registered`, `preliminary`, `final`, `amended`, `corrected`, `cancelled`, `entered-in-error`, `unknown`. Use `"final"` for a result you would hand the patient. |
| `code` | yes (1..1) | What was observed. Usually a LOINC code. |
| `subject` | no (0..1), but practically always sent | Reference to the Patient. |
| `effectiveDateTime` or `effectivePeriod` | no | When the observation applies. Almost always sent for clinical data. |
| `valueQuantity` (or one of the other `value[x]` shapes) | no | The actual value. Optional because some Observations record only an interpretation or a Boolean. |
| `category` | no | A high-level grouping like `laboratory`, `vital-signs`, `exam`. Required by US Core but not the base spec. |

The smallest valid Observation is `{resourceType: "Observation", status: "final", code: {...}}`. Anything beyond that is content, not structure.

### Condition (the diagnosis, problem, concern)

| Field | Required? | Notes |
|---|---|---|
| `resourceType` | yes | `"Condition"`. |
| `code` | no (0..1) | The condition itself. Almost always sent. |
| `subject` | yes (1..1) | Reference to the Patient. |
| `clinicalStatus` | conditionally required | Required if `verificationStatus` is anything other than `entered-in-error`. |
| `verificationStatus` | no (0..1) | `provisional`, `differential`, `confirmed`, `refuted`, `entered-in-error`. |

Condition is one of the FHIR resources where the minimum schema is permissive (only `subject` is hard-required) but the practical requirements for a usable clinical record are much higher. Conformance to US Core or similar profiles adds most of what you would actually want.

### MedicationRequest (the order for a medication)

| Field | Required? | Notes |
|---|---|---|
| `resourceType` | yes | `"MedicationRequest"`. |
| `status` | yes (1..1) | `active`, `on-hold`, `cancelled`, `completed`, `entered-in-error`, `stopped`, `draft`, `unknown`. |
| `intent` | yes (1..1) | `proposal`, `plan`, `order`, `original-order`, `reflex-order`, `filler-order`, `instance-order`, `option`. |
| `medicationCodeableConcept` or `medicationReference` | yes (one of) | The drug. Either inline (RxNorm code) or a reference to a Medication resource. |
| `subject` | yes (1..1) | Reference to the Patient. |
| `dosageInstruction` | no (0..*) | The dose/route/frequency. Free text plus structured fields. |

### Encounter (the visit)

| Field | Required? | Notes |
|---|---|---|
| `resourceType` | yes | `"Encounter"`. |
| `status` | yes (1..1) | `planned`, `arrived`, `triaged`, `in-progress`, `onleave`, `finished`, `cancelled`, `entered-in-error`, `unknown`. |
| `class` | yes (1..1) | The encounter class (e.g., `AMB` for ambulatory, `IMP` for inpatient). A Coding from a specific value set. |
| `subject` | no (0..1), almost always sent | Reference to the Patient. |
| `period` | no | Start and end times of the encounter. |
| `participant` | no | Who was involved. References Practitioners. |

These four resources cover most of what you will author by hand. The rest of the 150 resource types follow the same pattern: a spec page lists the fields and their cardinalities; the minimum is small; the practical minimum (what makes the resource useful clinically) is larger.

## 2. Profiles: constrained base resources

The base spec for Observation says `category` is optional and `valueQuantity` can be present or absent. That looseness is deliberate: the same resource type has to serve a CRP result, a blood pressure reading, a smoking-status assertion, and a 6-minute walk test, and the base spec is the union of what they all need.

A **profile** is a constrained version of a base resource for a specific use case. The US Core Observation Lab profile, for example, says:

- `status` must be present (already required by the base, but the profile re-confirms it).
- `category` must include the `laboratory` coding (no longer optional).
- `code` must come from a specific value set (LOINC lab codes).
- `subject` must be present and reference a US Core Patient.
- `effectiveDateTime` or `effectivePeriod` must be present.
- `valueQuantity` or one of the other value variants must be present (no value-less lab Observations).

A receiving system that "supports US Core Observation Lab" can rely on those guarantees. Without the profile, the receiver would have to check every field defensively. With the profile, the receiver knows the structure.

In the resource itself, conformance to a profile is declared in `meta.profile`:

```json
{
  "resourceType": "Observation",
  "meta": {
    "profile": [
      "http://hl7.org/fhir/us/core/StructureDefinition/us-core-observation-lab"
    ]
  },
  ...
}
```

Most US clinical FHIR traffic conforms to US Core profiles. Other implementation guides (mCODE for oncology, IPS for international patient summary, CARIN BB for payer data) define their own profiles for their own use cases. Track 4 walks profiles and implementation guides systematically; this track introduces them only enough to use the US Core ones in the capstone.

## 3. Must-support is not what it sounds like

The most-confused concept in FHIR.

**Cardinality** (`0..1`, `1..1`, etc.) is about whether a field is required. `1..1` means exactly one is required; `0..1` means it is optional. Cardinality applies to the sender: the sender must produce the field if cardinality is 1+.

**Must-support** is about whether a *receiver* must handle the field. A field marked must-support means: if the sender sends this field, the receiver has to know what to do with it (display it, store it, not silently drop it). Must-support does not change cardinality. A field can be must-support and still have cardinality `0..1`.

Concretely: US Core Patient marks `race` as must-support. A US-Core-conforming sender does not have to send race (it is optional). But a US-Core-conforming receiver that gets a Patient with race included must know what to do with it. If the receiver silently drops the race field, the receiver is non-conformant.

The most common misreading: "must-support means I must send it." It does not. Must-support is a contract on the receiver, not the sender.

The second most common misreading: "must-support means the field is meaningful." All fields in FHIR are meaningful; must-support is a stronger guarantee about end-to-end handling, not about whether the field exists.

Read must-support fields in a profile as: "if this field shows up in a resource conforming to this profile, both sides have agreed to handle it properly."

## 4. Extensions: adding what the base does not have

FHIR's base resources are deliberately minimal so they generalize internationally. When a US-specific concept like race or ethnicity needs to be attached to a Patient, the base spec does not have a field for it. FHIR's answer is the **extension**.

An extension is an object inside the `extension[]` array of any resource (or any element of any resource). It has a `url` naming what the extension is and a `value[x]` (or nested `extension[]` for complex extensions). The `url` is the canonical identifier of the extension's definition.

US Core race on a Patient:

```json
"extension": [
  {
    "url": "http://hl7.org/fhir/us/core/StructureDefinition/us-core-race",
    "extension": [
      {
        "url": "ombCategory",
        "valueCoding": {
          "system": "urn:oid:2.16.840.1.113883.6.238",
          "code": "2106-3",
          "display": "White"
        }
      },
      {
        "url": "text",
        "valueString": "White"
      }
    ]
  }
]
```

This is a *complex* extension: the outer extension has no value of its own, but contains an inner `extension[]` array. The inner extensions hold the actual data: an OMB-category coding and a free-text override.

Two practical rules.

- **Do not invent extensions casually.** Every extension should have a definition somewhere (in an implementation guide, or registered with HL7). Reusing existing extensions is almost always better than minting new ones.
- **Read the URL as the source of truth.** The `url` field tells you exactly which extension definition is in play. If you do not recognize the URL, look it up before doing anything with the value.

US Core publishes about thirty extensions covering US-specific data needs (race, ethnicity, birth sex, gender identity, tribal affiliation, and so on). Most US-Core-conforming Patient resources you see in the wild use a handful of them.

## 5. The `$validate` endpoint

A FHIR server exposes a special endpoint called `$validate` that takes a resource and reports back what is wrong with it. The pattern:

```
POST <base>/<ResourceType>/$validate
Content-Type: application/fhir+json

{resource as JSON body}
```

The response is an **OperationOutcome** resource: a list of `issue[]` entries, each with a severity (`fatal`, `error`, `warning`, `information`), a code (categorizing the issue), and a diagnostics string describing what is wrong.

A clean validation (a well-formed Observation pointing at a patient who exists on the server, with all profile constraints satisfied) returns an OperationOutcome with no `issue[]` array, or with only informational entries.

A broken validation returns errors like:

```
[error] Observation.status: minimum required = 1, but only found 0
[error] Observation.code: minimum required = 1, but only found 0
```

A few realities to expect.

- **References to resources that do not exist on the server come back as errors.** If you `$validate` an Observation that references `Patient/elena-reyes` against a server that does not have that patient, you get an "Unable to resolve resource" error. This is true even if the rest of the resource is perfect. Most production validators relax this; some do not.
- **Servers that do not have every code system loaded return warnings.** "CodeSystem is unknown and can't be validated: http://loinc.org" is common. The resource is still valid; the validator cannot fully check the codes.
- **Best-practice constraints surface as warnings.** Things like "resources should have narrative for robust management" (the dom-6 constraint) or "observations should have a performer" are recommendations, not errors. You can ignore them when starting; you should not ignore them in production.

Reading an OperationOutcome takes two passes. Pass 1: look only at `severity = error` and `fatal` issues. Those prevent the resource from being valid. Pass 2: look at warnings to understand what a careful receiver would still complain about.

## 6. Transaction bundles: posting multiple resources at once

A clinical visit usually produces several related resources: an Encounter, a few Observations, sometimes a new Condition or a MedicationRequest. You could `POST` each one separately. FHIR offers a cleaner option: a **transaction bundle**.

A transaction bundle is a Bundle of `type: "transaction"` whose entries each carry a `request` object describing what to do. The server applies all the operations atomically: either every entry succeeds or none of them do.

```json
{
  "resourceType": "Bundle",
  "type": "transaction",
  "entry": [
    {
      "resource": { "resourceType": "Observation", ... },
      "request": { "method": "POST", "url": "Observation" }
    },
    {
      "resource": { "resourceType": "Observation", ... },
      "request": { "method": "POST", "url": "Observation" }
    },
    {
      "resource": { "resourceType": "Encounter", ... },
      "request": { "method": "POST", "url": "Encounter" }
    }
  ]
}
```

The receiving server processes each entry and returns a `transaction-response` bundle with the results.
