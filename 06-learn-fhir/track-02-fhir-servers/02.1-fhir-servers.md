## What a FHIR server actually is

A **FHIR server** is a web service that speaks FHIR over HTTP. You send it requests; it sends back responses. There is no other ceremony.

Point a browser at `https://hapi.fhir.org/baseR4/Patient/90286136` (a real address; the patient may still be there when you read this) and you are sending an HTTP `GET` request. The server walks its database, finds the Patient resource with id `90286136`, serializes it as JSON, and sends it back. The browser displays the JSON because the browser does not know what else to do with it. A FHIR client would parse the JSON and render it as something useful: a chart, a search result, an EHR widget.

Every interaction in this track follows the same pattern.

1. You build a URL.
2. Your code sends a `GET` request to that URL.
3. The server returns a JSON response.
4. Your code parses the JSON and does something with it.

The hard part of FHIR is not the protocol. The protocol is web-standard plumbing every developer has used. The hard part is the *content*: which resources to ask for, which search parameters to use, what shape the response takes, what the clinical fields mean. Track 1 was that content. Track 2 is the plumbing.

## A gentle Python introduction

The smallest possible Python that calls a FHIR server:

```python
import requests
url = "https://hapi.fhir.org/baseR4/metadata"
resp = requests.get(url, headers={"Accept": "application/fhir+json"})
data = resp.json()
```

Read line by line:

- **`import requests`.** Bring in the standard Python HTTP library. ("Standard" in the sense of "everyone uses it." It is not in the Python standard library, but it is the de facto choice.)
- **`url = ...`.** The full address of the resource. The `/metadata` endpoint on any FHIR server returns the server's CapabilityStatement, which describes what the server can do.
- **`resp = requests.get(url, ...)`.** Send an HTTP `GET` request to that URL. The `headers` argument tells the server we want FHIR JSON back. (Without that header, some servers default to XML.)
- **`data = resp.json()`.** Parse the JSON body of the response into a Python dictionary. From here on, `data` behaves like any nested dictionary: `data["resourceType"]`, `data["software"]["name"]`, and so on.

That is the entire client. Real production code adds error handling, retries, authentication, and async, but the core remains those four lines.

This curriculum uses a thin wrapper around `requests` called `shared.fhir_compat.fhir_get()` so the same notebook also runs in WASM-served Marimo (where the browser sandbox cannot use `requests` synchronously). The wrapper has the same signature: pass a URL, get back a parsed dictionary. The notebook uses it where it matters; this essay sticks with `requests` because it is what you would use in any normal Python project.

## Building search URLs

The URL pattern for a FHIR search:

```
<base>/<ResourceType>?<param>=<value>&<param>=<value>...
```

Worked example: every CRP result for one patient since 2024, newest first, with the patient resource included in the response:

```
GET https://hapi.fhir.org/baseR4/Observation
    ?subject=Patient/elena-reyes
    &code=http://loinc.org|1988-5
    &effective-date=ge2024-01-01
    &_sort=-date
    &_include=Observation:patient
    &_count=50
```

Three things to notice in that URL:

- **The system goes with the code.** `code=http://loinc.org|1988-5` says "the LOINC code 1988-5," not "any code that happens to share those digits." For LOINC this barely matters; for SNOMED and ICD-10 it matters a lot, because the same digit string is often a valid code in multiple vocabularies.
- **Comparators are two-letter prefixes.** `ge` for greater-or-equal, `gt` for greater-than, `le`, `lt`, `eq`, `ne`. The URL is a query string and cannot carry `>`, `>=`, `<` reliably across all HTTP intermediaries, so FHIR picked letter prefixes instead.
- **Underscored parameters are general.** `_sort`, `_count`, `_include`, `_revinclude`, `_format`, `_pretty` apply to every resource type. Parameters without the underscore (`subject`, `code`, `date`) are resource-specific and defined in the FHIR spec page for the resource.

The full list of search parameters for any resource type lives in the FHIR R4 spec at the bottom of that resource's page. Observation has about thirty defined parameters. Patient has about twenty. MedicationRequest about fifteen. Look them up when you need them; do not memorize them.

## Parsing searchset bundles

Every search response is a Bundle of `type: "searchset"`. The shape is uniform:

```json
{
  "resourceType": "Bundle",
  "type": "searchset",
  "total": 18,
  "link": [
    {"relation": "self", "url": "..."},
    {"relation": "next", "url": "..."}
  ],
  "entry": [
    {
      "fullUrl": "https://server/Observation/abc123",
      "resource": { "resourceType": "Observation", "id": "abc123", ... },
      "search": { "mode": "match" }
    },
    {
      "fullUrl": "https://server/Patient/xyz789",
      "resource": { "resourceType": "Patient", "id": "xyz789", ... },
      "search": { "mode": "include" }
    }
  ]
}
```

Read it once and the parsing pattern becomes obvious. In Python:

```python
bundle = resp.json()
assert bundle["resourceType"] == "Bundle"
for entry in bundle.get("entry", []):
    resource = entry["resource"]
    rtype = resource["resourceType"]
    # do something with the resource
```

Two small details that catch people off guard:

- **Not every server reports `total`.** Some servers omit it for performance (counting all matches is expensive). Do not rely on `total` being present; rely on the actual entry count.
- **`search.mode` distinguishes matches from includes.** When you use `_include`, the response contains both the resources matching your search and the resources they reference. The `mode` field tells you which is which: `match` means it matched your search, `include` means it was pulled along because something else referenced it.

The pattern of "look at each entry, check the resource type, branch on it" is most of what FHIR client code does. Track 1's bundle was a `collection`; the entries had no `search` field but were otherwise identical in shape.

## Pagination

If the server returned a `next` link in `bundle["link"]`, there are more results to fetch. The pattern:

```python
def collect_all(start_url):
    results = []
    url = start_url
    while url:
        bundle = fhir_get(url)
        for entry in bundle.get("entry", []):
            results.append(entry["resource"])
        url = next_link(bundle)
    return results

def next_link(bundle):
    for link in bundle.get("link", []):
        if link.get("relation") == "next":
            return link["url"]
    return None
```

The `next` URL is opaque from the client's perspective. Do not parse it; fetch it. The server constructs it however it wants (some embed encrypted continuation tokens, some put the offset directly in the URL). Your client treats it as a black-box pointer to the next page.

Two practical notes:

- **Page size is determined by `_count`.** Smaller pages mean more HTTP round trips; larger pages mean larger responses. Most production code uses 50 to 200 per page. The server may cap your `_count` (it is a hint, not a requirement).
- **`_count=0` returns the count without the data.** Useful when you want to know "how many of these does the server have?" without paying for the body.

## Real test servers behave like real test servers

`hapi.fhir.org` is the most-used public FHIR test server. It is free, it speaks fluent FHIR R4, and it accepts both reads and writes from anyone on the internet. That last fact matters: anyone on the internet can write anything to hapi.fhir.org. The data there is wildly inconsistent. Patient names include test strings like "Test Foo Bar." Some resources reference patients that have been deleted. Search results include partial data from a dozen different test scenarios from a dozen different organizations.

This is realistic. Production FHIR servers have their own quality issues; the quirks of hapi.fhir.org are an underdamped version of what you will see at every site. Three habits help:

1. **Validate the resourceType before reading any other field.** Defensive parsing prevents one malformed entry from breaking your loop.
2. **Treat string fields as potentially malformed.** The patient name "Karla NuÃ±ez" you will see in this track is real, sitting on hapi.fhir.org as this is written. It is a UTF-8-mojibake artifact from whoever wrote that record. Production data has equivalents.
3. **Use `_format=json` explicitly.** Some servers default to XML if your Accept header does not make JSON unambiguous.

The capstone in this track avoids these quirks by using a synthetic cohort fixture: a hand-crafted searchset bundle with five RA patients on consistent data. That lets you focus on the parsing and the trend chart without the test-server noise. The skills you build there are the same skills you would use against any production server.

## What to carry into Track 3

When the rest of the course (Tracks 3 through 5) starts asking you to **write** FHIR resources, the four patterns above stay the same in reverse:

- The URL pattern. Writing is a `POST` to `<base>/<ResourceType>` (server picks the new id) or a `PUT` to `<base>/<ResourceType>/<id>` (you pick the id, the server validates).
- The body shape. The thing you `POST` or `PUT` is a single resource, structured the same way the server hands them back to you.
- The response. Successful writes return the stored resource (often with server-added fields like `meta.versionId`, `meta.lastUpdated`).
- The validation. Production servers reject resources that do not conform to required profiles. Track 4 walks profiles and conformance.

Track 3 picks up from there.
