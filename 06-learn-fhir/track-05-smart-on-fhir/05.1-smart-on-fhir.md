## SMART is another IG

Most introductions to SMART on FHIR start with OAuth and lose the reader in flows, redirects, scopes, and JWTs. There is a simpler frame.

SMART on FHIR is an **implementation guide**. It is published at `hl7.org/fhir/smart-app-launch`, it has a version (currently 2.x), and it has the same structural pieces you saw in Track 4: a set of profiles, some new fields the base FHIR spec does not have (here, mostly metadata on CapabilityStatement and OAuth flows), value sets for the scopes, a CapabilityStatement for what a SMART-enabled server has to support, and examples. The SMART spec is bigger than the average IG because OAuth itself is involved, but it is structurally a SMART IG layered on top of US Core.

With Track 4's IG-reading vocabulary in place, the SMART spec reads as: "a FHIR server is SMART-enabled if it advertises specific OAuth endpoints in `/.well-known/smart-configuration`, accepts certain `scope` strings in authorization requests, returns access tokens that carry launch context (patient, encounter, user), and exposes its resources behind that token gate."

The rest of this essay covers the four parts a clinician evaluating a SMART app needs to understand: what an app is, how it launches, what scopes it gets, and where CDS Hooks and Bulk Data fit alongside. One piece of vocabulary comes first.

---

## Authentication is not authorization

Two terms that get used interchangeably and should not be.

**Authentication** (often abbreviated **authn**) answers *who you are*. The act of proving identity. "I am Dr. Bennett." The mechanism could be a password plus a second factor, a smart card, a biometric, or a digitally signed credential. The end product is the server being convinced that the entity on the other end is who they claim to be.

**Authorization** (often abbreviated **authz**) answers *what you are allowed to do*. The act of granting access to specific resources or operations. "Dr. Bennett is allowed to read Ms. Reyes's chart." Authorization happens *after* authentication: the system first figures out who you are, then decides what you can do.

Shorthand: **authn is who, authz is what.**

The two are independent. A clinician can be authenticated (the system knows it really is Dr. Bennett) and still be unauthorized for a specific action (Dr. Bennett is on staff but is not on this patient's care team, so reading the chart is blocked). The reverse also matters: an authenticated user might have broad authorization that the application does not need (Dr. Bennett can read the whole chart, but the RA monitoring app should only be able to read what is relevant to RA).

**Why SMART has to address both:**

- A FHIR server holds patient data. Every request to it has to answer two questions: *who is asking?* (authn) and *what is this request allowed to read or write?* (authz).
- SMART uses **OpenID Connect** (a thin layer on top of OAuth 2.0) for the authn answer. When your app requests the `openid fhirUser` scopes, the token response includes an `id_token` (a signed JWT) carrying claims about which user is logged in.
- SMART uses **OAuth 2.0 scopes** for the authz answer. The access token, presented on every FHIR request as `Authorization: Bearer <token>`, encodes which resources and operations the bearer is allowed to perform.
- **Launch context** is a third axis on top of those two. Even within what is authorized, the launch context narrows the *current focus*. The token might authorize reading any patient the user can see, but the launch context says "this session is about Ms. Reyes specifically."

A useful analogy for the three:

- **Authentication** is the bouncer at the door checking your ID.
- **Authorization** is the wristband that says which areas of the venue you can access.
- **Launch context** is your seat assignment for tonight's show.

The OAuth flow described later in this essay is doing all three at once. Knowing which step is answering which question keeps the flow legible.

## What a SMART app is

A SMART app is a web (or native) application that reads from and optionally writes to a FHIR server, using OAuth 2.0 (specifically the authorization-code-with-PKCE flow) to authenticate. It is *substitutable*: the same app can plug into any SMART-enabled EHR without modification, because the EHR exposes a standard launch surface.

Substitutability is the point of the IG. Before SMART, building an app that worked inside Epic and Cerner meant writing two completely different integrations. After SMART, you write one app that uses the SMART launch protocol; the same app launches inside any SMART-enabled EHR.

The app itself lives outside the EHR. The EHR does not host it; the EHR launches it (in an iframe or an external window) and hands it a launch context plus an access token. The app uses the access token to read and write FHIR resources back at the EHR's FHIR server.

---

## The two launch flavors

There are two ways a SMART app starts up. Most apps support one; some support both.

### EHR launch

The clinician is logged into the EHR. They click a button somewhere in the EHR (often a sidebar, an order-entry add-on, or a chart-summary widget) that launches the app. The EHR:

1. Generates a one-time **launch context** containing the patient currently in focus, the encounter (if any), the user (the clinician), and an opaque launch token.
2. Redirects the user's browser to the app's launch URL, passing two query parameters: `iss` (the FHIR server's base URL) and `launch` (the launch token).
3. The app reads `iss`, fetches `iss/.well-known/smart-configuration` to discover the OAuth endpoints, and initiates the OAuth flow.

This is the dominant flow for clinical workflow apps: the clinician's context is already established by the EHR, the app inherits it, and the user never has to log in a second time.

### Standalone launch

The clinician (or patient, for patient-facing apps) starts at the app directly. The app knows which FHIR server to talk to (configured ahead of time, or chosen from a list) but has no launch context. The app initiates the OAuth flow directly with the FHIR server, and the user has to authenticate. The token response still carries patient context if the user has access to multiple patients and picks one during the auth flow.

This is the flow for patient-facing apps and for clinician apps that are not launched from inside an EHR (e.g., an analytics tool a researcher uses against a cohort).

The IG calls these flavors `launch-ehr` and `launch-standalone`. A SMART-enabled server's CapabilityStatement lists which it supports.

## The OAuth dance, in plain English

The actual OAuth 2.0 authorization-code-with-PKCE flow, what every SMART app does after launch, broken into the steps that matter clinically.

1. **Discover.** The app fetches `<fhir-base>/.well-known/smart-configuration` and reads the `authorization_endpoint` and `token_endpoint` URLs.
2. **Authorize.** The app redirects the browser to the authorization endpoint with a query string naming itself (the `client_id`), the scopes it wants, where to redirect back to (`redirect_uri`), a state token (to prevent CSRF), and a PKCE code challenge (to prove later that the app that finishes the flow is the same one that started it).
3. **User consents (or the EHR auto-grants).** In EHR launch, the EHR usually auto-grants the scopes that match the existing user's permissions. In standalone launch, the user sees a consent screen and approves the scopes.
4. **Authorization code returned.** The authorization endpoint redirects the browser back to the app's `redirect_uri` with a one-time `code` parameter.
5. **Token exchange.** The app POSTs the `code`, its `client_id`, the `redirect_uri`, and the PKCE code verifier to the token endpoint. The server validates everything and returns a token response containing the **access token**, the **scope** actually granted (which may be narrower than what was requested), an **expiration**, optionally a **refresh token**, and the **launch context** fields (`patient`, `encounter`, etc.).
6. **API calls.** The app makes FHIR requests against the FHIR base URL, passing the access token as `Authorization: Bearer <access_token>`. Every request is scoped by what the token allows.

The cryptographic parts (PKCE, JWT signatures) are handled by libraries. The clinically interesting parts are the **scope** strings and the **launch context** fields. Those determine what the app can read, write, and see.

## Scopes

A SMART scope is a string that describes what the app wants. The vocabulary has three pieces.

**Context scopes** request launch context.

- `launch`: the EHR launch context (patient + encounter + whatever the EHR provides).
- `launch/patient`: standalone launch with a patient-picker step.
- `launch/encounter`: standalone launch with an encounter-picker step.
- `openid fhirUser`: the identity of the launching user, returned as an OpenID Connect ID token.
- `offline_access`: the app wants a refresh token (i.e., persistent access beyond the user's active session).

**Resource scopes** request access to FHIR resources, parameterized by who and what.

The shape is `<context>/<ResourceType>.<operation>`, where `<context>` is `patient` (data for the launch-context patient only), `user` (data the launching user is authorized to see, across patients), or `system` (data accessible regardless of user, used by backend services).

Examples:

- `patient/Observation.read`: read observations for the launch-context patient only.
- `user/Patient.read`: read patients the launching clinician has access to.
- `patient/*.read`: read every resource type for the launch-context patient (a common ask for chart-viewer apps).
- `user/*.write`: write any resource as the launching user (rare; usually you ask for specific resource types).
- `system/Observation.read`: backend service reading observations across the whole population (Bulk Data territory).

**Granular scopes** (SMART v2) let you narrow further with query parameters. `patient/Observation.read?category=laboratory` requests read access only to laboratory observations for the launch-context patient. The granular-scope spec is newer; older servers may not support it.

A request typically combines context scopes and resource scopes:

```
launch openid fhirUser patient/Observation.read patient/Condition.read offline_access
```

The server returns the *granted* scope in the token response, which may be a strict subset of what the app asked for. The app has to handle the case where it got less than it wanted.

---

## Launch context, in detail

The token response that comes back from the token endpoint includes more than the access token. It carries the **launch context**: the IDs of the resources the app should focus on. The most common fields:

- `patient`: the patient ID. The app uses this to scope its FHIR queries: `GET /Observation?subject=Patient/<patient>&...`.
- `encounter`: the encounter ID if the launch was associated with one.
- `id_token`: a JWT carrying identity claims about the launching user (the clinician). Decoded, it has fields like `sub` (the user's identifier on this server), `fhirUser` (a reference to a Practitioner resource), and `profile`. The app uses this to know which clinician is using it.

Launch context is what makes the app substitutable. The app does not ask "who is the patient?" through a UI; the EHR already knows, and it tells the app via the token response.

## CDS Hooks, at concept level

CDS Hooks is a separate spec from SMART on FHIR, but they often appear together. SMART is for **user-launched apps**; CDS Hooks is for **event-driven services**.

A CDS Hooks service is a small web service the EHR calls at specific workflow moments. The most common moments (the "hooks") are:

- `patient-view`: the clinician opens a patient's chart. Fires once per chart open.
- `order-select`: the clinician has started entering an order but not yet signed it. Fires as the order is being composed.
- `order-sign`: the clinician is about to sign an order. Fires before the signature commits.

The EHR sends a JSON request to the CDS service's URL with the FHIR context (patient ID, encounter ID, the draft order). The service responds with a list of **cards**: small UI elements containing a summary, optional detail text, optional source links, and optional **suggestions** (proposed alternative actions). The EHR renders the cards in the user's workflow.

CDS Hooks uses FHIR resources as its data payload but is not itself a FHIR API. The service typically reads from the EHR's FHIR server (sometimes via a SMART scope granted to the service) to gather what it needs to decide what cards to return.

Course 12 (Clinical decision support) walks CDS Hooks in detail. For this track, knowing the three common hooks and the request/cards pattern is enough.

## Bulk Data ($export), at concept level

Bulk Data (officially "FHIR Bulk Data Access IG") is for **population-scale data access**. Where the SMART App Launch flow scopes a request to one patient (`patient/Observation.read`), Bulk Data is for "give me observations for everyone in this group, asynchronously."

The flow:

1. The client (typically a research or analytics backend) authenticates with `system/*` scopes via the "backend services" SMART variant (no user, only a signed JWT proving the client is who it claims to be).
2. The client issues an `$export` operation on a Group, Patient, or the system root. This is an async operation; the server returns a `202 Accepted` with a status-polling URL.
3. The client polls the status URL until the server reports completion. The response includes a list of NDJSON file URLs, one per resource type.
4. The client downloads the NDJSON files and processes them.

Bulk Data is what powers most modern FHIR-based research and quality measurement. The IG is at `hl7.org/fhir/uv/bulkdata`. For everyday clinical app work, you will not write Bulk Data clients. For research and population health, you will.

## What an evaluator of a vendor's SMART app should ask

A clinical informaticist evaluating a vendor's SMART app should be able to read the app's documentation and check, with this track's vocabulary:

1. Which launch flavor does it support? `launch-ehr`? `launch-standalone`? Both?
2. Which scopes does it request? Are they narrow (only what it needs) or broad (`patient/*.*`)? An app requesting wider scopes than its function justifies is a yellow flag.
3. Does it use `offline_access`? If yes, what is its data-retention policy after the user's session ends?
4. Does it read or write FHIR resources beyond what its clinical purpose requires? Read the scopes; that is the contract.
5. Does it register CDS Hooks services? If yes, which hooks, and what cards does it return?
6. Does it use Bulk Data? If yes, what does it do with the data after it pulls it?

The right answer to each is not "the smallest possible scope." It is "the smallest scope that lets the app do its clinical job." The wrong answer is "we always request `patient/*.*` and `offline_access` so we never have to deal with permission errors." That answer is common, and it is how you end up with vendor apps that exfiltrate more data than they should.
