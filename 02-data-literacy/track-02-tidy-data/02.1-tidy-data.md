## The one rule

A dataset is **tidy** when three things are true at once:

1. **Each row is one observation.** One specimen, one visit, one medication exposure, one fact.
2. **Each column is one variable.** One thing being measured, one attribute, one identifier.
3. **Each cell holds one value.** Not two things glued together. Not a list. Not a free-text blob that contains five facts.

The rule comes from Hadley Wickham's 2014 paper "Tidy Data," which named a pattern data analysts had been using and arguing about for decades. The contribution was not the shape; it was naming the shape so people could ask "is this tidy?" out loud and get an answer.

Most clinical data wrangling is moving data into this shape and then doing the analysis. Once the data is tidy, every subsequent move is short. While the data is untidy, every subsequent move is a paragraph of pandas with three caveats. The cost of not tidying is paid every time you touch the dataset.

## The four shapes of untidy data you meet in practice

### 1. Wide-when-it-should-be-long

A flowsheet export with one row per timestamp and one column per vital sign:

| time | hr | bp_sys | bp_dia | temp | rr | spo2 |
|---|---|---|---|---|---|---|
| 08:00 | 88 | 132 | 84 | 37.1 | 16 | 98 |
| 12:00 | 92 | 138 | 86 | 37.4 | 18 | 97 |

The variable here is *vital sign* and the value is *the measurement*. The columns `hr`, `bp_sys`, and so on are not variables. They are values of a single variable (the vital sign's identity) that the table mis-shaped as columns.

A tidy version has one row per measurement:

| time | vital_sign | value |
|---|---|---|
| 08:00 | hr | 88 |
| 08:00 | bp_sys | 132 |
| 08:00 | bp_dia | 84 |
| 08:00 | temp | 37.1 |
| ... | ... | ... |

Most filtering, grouping, and plotting is short in long form. Mean blood pressure during a shift is one `groupby`, not a loop over columns. Plotting all six vitals on one chart with color-by-vital is one Altair call, not six.

### 2. Long-when-it-should-be-wide

The opposite problem. A lab table with one row per lab result:

| date | test | value |
|---|---|---|
| 2024-04-17 | CRP | 18.7 |
| 2024-04-17 | ESR | 29 |
| 2024-04-17 | ALT | 38 |

This is long-format, which is tidy for many purposes. But when the unit of analysis is the visit (CRP, ESR, and ALT side by side for a flare check), the wide form fits better:

| date | CRP | ESR | ALT |
|---|---|---|---|
| 2024-04-17 | 18.7 | 29 | 38 |

Both shapes are tidy under the right framing. The right shape is the one where each row is the observation you care about. For trends, long. For visit-level summaries, wide. The move between them is the same operation in two directions.

### 3. Two-facts-in-one-cell

A dose-and-route column:

| medication | dose_route |
|---|---|
| Methotrexate | 25 mg SC weekly |
| Adalimumab | 40 mg SC q2wk |
| Folic acid | 1 mg PO daily |

The cell `25 mg SC weekly` contains four separate facts: dose magnitude (25), dose unit (mg), route (SC), frequency (weekly). To compute "is this patient on a high-dose biologic," you need the magnitude alone. To filter to "subcutaneous medications," you need the route alone. With everything glued together, every filter becomes a regular expression.

Tidy version:

| medication | dose_value | dose_unit | route | frequency |
|---|---|---|---|---|
| Methotrexate | 25 | mg | SC | weekly |
| Adalimumab | 40 | mg | SC | q2wk |
| Folic acid | 1 | mg | PO | daily |

A `split` is the move. The challenge is that the format is not always uniform: `"25 mg SC weekly"` and `"25mg subq weekly"` look identical to a human and very different to a parser.

### 4. Repeating groups

The clinical extract that came out of a forms-based system that thought "medications" was a one-to-many relationship and decided to flatten it as columns:

| patient | med1 | dose1 | med2 | dose2 | med3 | dose3 | med4 | dose4 |
|---|---|---|---|---|---|---|---|---|
| ER-001 | MTX | 25 mg | Adalimumab | 40 mg | Folic acid | 1 mg | | |
| ER-002 | MTX | 20 mg | | | | | | |

The columns `med1`, `med2`, `med3`, `med4` are not four variables. They are the same variable (medication name) repeated four times because the patient might have up to four medications. The right shape is one row per medication exposure:

| patient | medication | dose |
|---|---|---|
| ER-001 | MTX | 25 mg |
| ER-001 | Adalimumab | 40 mg |
| ER-001 | Folic acid | 1 mg |
| ER-002 | MTX | 20 mg |

The reshape is a `melt` followed by some grouping. Repeating groups are the most common shape problem in clinical extracts because they are how spreadsheet-shaped tools represent one-to-many data.

## What `melt` and `pivot` actually do

Most reshaping is one of two pandas operations. Both sound technical and are conceptually simple.

### `melt` makes wide into long

`melt` takes a set of columns and stacks them into two: a *variable* column that names which original column each value came from, and a *value* column that holds the value itself. The other columns (the **id_vars**) are repeated for each new row.

Wide vitals, melted into long:

```python
long_vitals = wide_vitals.melt(
    id_vars=["time"],
    value_vars=["hr", "bp_sys", "bp_dia", "temp", "rr", "spo2"],
    var_name="vital_sign",
    value_name="value",
)
```

The wide table had one row per timestamp. The long table has one row per (timestamp, vital sign). The information is the same; the shape is different.

### `pivot` makes long into wide

`pivot` is the inverse. It takes a long table and spreads one variable column out into multiple value columns:

```python
wide_labs = long_labs.pivot(
    index="date",
    columns="test",
    values="value",
)
```

The long table had one row per (date, test). The wide table has one row per date with one column per test. Same information, different shape.

The two operations are inverses. A `melt` then a `pivot` (with matching parameters) returns the original. Which shape you want is determined by the analysis that comes next, not by the shape the data arrived in.

A note on `pivot_table` versus `pivot`. `pivot` assumes each (index, column) pair has exactly one value, and errors if there are duplicates. `pivot_table` lets you specify an aggregation function (`mean`, `sum`, `count`) to handle duplicates, which fits when the same patient had two CRPs drawn on the same day. In clinical data, duplicates happen, so `pivot_table(aggfunc="mean")` is the safer default.
