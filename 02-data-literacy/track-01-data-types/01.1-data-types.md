# Data types and why they matter

A reference companion to the notebook. Read it first, after, or not at all. The notebook is where the type bugs show themselves.

---

## Why type is the first question to ask of a column

Every column in a clinical dataset has a **type**. The type is the rule that says what values the column may hold and which operations on those values are legal. The type is what lets "the average CRP in this cohort was 22 mg/L" actually be the average of CRP measurements rather than the average of something pretending to be CRP.

Most failed clinical analyses break in the first three commands: read the file, filter to the cohort, compute a summary. The summary comes out plausibly, the cohort comes out the right size, and one column had a type nobody checked. The downstream is consistent with the upstream. The upstream was wrong.

The fix is routine. Look at each column. Ask what type it is and what that type lets you do. The answer is usually obvious. The work is doing the check at all.

---

## The four data types you actually use

Every clinical dataset is some combination of four types. The list is not exhaustive (booleans, blobs, geographic shapes, hierarchical objects), but four covers most of the work.

### 1. Numbers (continuous and integer)

The values you compute on. CRP in mg/L. ESR in mm/h. Hemoglobin in g/dL. Joint counts as integers. Age in years. The defining property is that mathematical operations on them are clinically meaningful: average, median, sum, range, difference between two values, ratio of two values.

There are two flavors. **Continuous** numbers (CRP, weight, blood pressure) admit any real value within their physical range. **Integer** numbers (joint counts, encounter counts, number of admissions in the last year) admit only whole values. A "mean number of admissions of 1.3" is informative even though no individual patient was admitted 1.3 times.

The most common bug with numeric columns is that they are not numeric. A single non-numeric cell anywhere in the column forces the entire column to be stored as text. The offending cell is often invisible: a leading apostrophe, a stray comma in a number, a `<5` sitting in an LFT column because the lab reports values below the limit of quantification as text. The column reads in fine. The mean comes out as an error or, worse, as nothing at all because the function silently skipped every value.

### 2. Text (strings)

Free narrative. The history of present illness, the assessment paragraph, the social history. Text is the most structurally flexible column type and the one you can do the least statistics on. Length, concatenation, and substring searches are the operations text supports cleanly. Averages and totals are not legal moves.

Text is also the default landing pad for anything else that fails to classify. Numbers fall into text when they have a typo. Dates fall into text when their format does not parse. Categories fall into text when they were never declared as categories. Most type bugs surface as "this column is text and should not be."

### 3. Dates and timestamps

Dates are difficult. They look like text. They behave like text in some operations and like numbers in others. They have at least six common written formats, three of which are ambiguous (does `03/04/2024` mean March 4 or April 3?). They have time zones. Time zones change with daylight saving time. The same instant has a different calendar date in San Diego and in Boston for two hours every night. An Excel cell can drift by a day because the time zone of the machine that opened the file disagreed with the time zone of the machine that saved it. None of this throws an error.

A date column is correct when:

- Every value parsed successfully (no silent NaT, no string that fell through the parser).
- Every value used the same format and the same time zone.
- The ordering operations (`<`, `>`, sort) produce a clinically sensible order.

The notebook walks five formats of the same date. They all look correct individually. Two of them produce a date two thousand years away from the others. One produces a different date depending on which country the parser thinks you are in.

### 4. Categorical (categories and codes)

Values that are not numbers and not free text. Sex (M, F, other, unknown). Race (categories). Encounter class (inpatient, outpatient, emergency). Diagnosis (an ICD-10 code). Medication (an RxNorm code or a name or both). Lab (a LOINC code, a name, or both).

A categorical column has a fixed (sometimes small, sometimes large) set of allowable values. The set is the **value set** for the column. "Sex" might be `{F, M, other, unknown}`. "Diagnosis" might be the full ICD-10-CM code book, all roughly 70,000 entries. Either way, the column means something specific when one of the allowed values is in the cell and something undefined when anything else is.

The same categorical fact can be written multiple ways in the same dataset. "Female." "F." "f." "Female " (with trailing whitespace). "2" (numeric encoding in some EHR exports). "362" (a Cerner-style sex_cd value). Six rows that are clinically the same patient population, six different categorical values to the computer. Until they are reconciled, "what fraction of the cohort is female" cannot be answered.

This is where coding systems come in. A coding system is a published, versioned vocabulary that names a list of allowed codes and what each one means. **LOINC** is a coding system for lab tests. **SNOMED CT** is a coding system for clinical concepts. **ICD-10-CM** is a coding system for diagnoses billable in the United States. **RxNorm** is a coding system for medications. **UCUM** is a coding system for units of measure.

A coded column is correct when:

- The value is from the declared coding system, not from a different one with similar-looking codes.
- The system the code came from is recorded somewhere (a `system` column, or a profile that says "this column always uses LOINC").
- The code has not been retired in the version of the system the rest of the data assumes.

Most cross-vendor data quality complaints decompose to one of these. "Their data is dirty" usually means "their data uses a different coding system than ours, and nobody told the analysis."

## The CRP-as-text bug in detail

CRP is a continuous numeric measurement. In `labs.csv` it lives in a column called `value`, alongside ESR, anti-CCP, hemoglobin, ALT, and creatinine. All of these are numeric. The column reads in as numeric, mean-of-CRP returns 22.4 mg/L, and the analysis proceeds.

Now consider a parallel universe in which the EHR reports values below the lower limit of quantification as text. Five out of ninety hemoglobin values come back as `"<2.0"` because they were drawn on an analyzer that flags very low values that way. Every numeric value in the column is still numeric in spirit. Five cells are now strings.

`pandas.read_csv` infers the column type by looking at every cell. The presence of those five strings means the entire column is now text. The cell `12.1` is now the string `"12.1"`. Mean-of-hemoglobin returns one of three things, depending on the toolchain:

- A `TypeError`, in the best case. The error says a numeric operation was attempted on a string column. You fix it.
- A silent skip, where the function drops the non-numeric values and computes the mean of what remains. The number is plausible. It is wrong, in a direction that overstates the true mean (the low-end values were the ones flagged).
- A character-wise sort, where `"12.1"` and `"7.4"` sort as if `"1"` came before `"7"`. The "minimum hemoglobin in the cohort" becomes the value whose first character is alphabetically smallest. The result is a typewriter ordering, not a clinical ordering.

Three failure modes, only one of which warns you. The other two ship to the slide deck.

The fix is to handle the non-numeric values explicitly. Drop them, replace them with the limit of quantification, or keep them as a separate flag. Whichever choice you make, make it on purpose. The bug is not that the data is messy. The bug is that the data is messy quietly.

## What "spot the type errors" actually looks like

Auditing a column for type errors is a five-question routine. The audit at the end of the notebook walks each step on a synthetic export of Ms. Reyes's labs.

1. **What type does the column claim to be?** What did the reader (`read_csv`, `read_excel`, the loader function) decide this column was?
2. **What type does the column need to be?** What is the clinical concept stored in this column? Numeric measurement, categorical code, date, free text?
3. **Where are the offenders?** If those two disagree, which rows broke the inference? A column that should be numeric but is text has at least one row whose value is not a number. Find it.
4. **Why is each offender there?** A typo (fixable), a sentinel value like `"<5"` (needs a decision), a unit mixed into the value cell like `"42 mg/L"` (separable), a different field pasted into the wrong column (different problem), or a real missing value coded with a non-standard placeholder like `"NULL"` or `"N/A"` (Track 03)?
5. **What is the fix?** Drop, replace, separate, or escalate. Pick one. Document which.

The routine takes ten minutes per column on a real dataset and prevents most of the downstream wreckage. The notebook walks one synthetic column through the full routine, then asks you to run it on a second column on your own.
