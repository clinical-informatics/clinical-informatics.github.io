# Null values and missingness

A reference companion to the notebook. Read it first, after, or not at all.

---

## What a null actually is

Before we talk about missingness, the data type. A **null** is the placeholder a system uses to mean "no value here." That is the definition. The complication is that every system you touch uses a slightly different placeholder, and the differences matter.

**In a relational database (SQL).** `NULL` is its own value in the language. It is not the number 0, not the empty string, not `false`. `NULL = NULL` evaluates to `NULL` (not `true`), which surprises every analyst the first time. To check whether a cell is missing, you write `WHERE column IS NULL`, not `WHERE column = NULL`. SQL has three-valued logic: true, false, null. Most clinical research bugs at the SQL layer are unhandled nulls in a join or a filter.

**In pandas.** Three things you might see in a "missing" cell:
- `NaN` (numpy's not-a-number). Used for missing numeric values. `NaN != NaN` is `True`, which is mathematically correct but surprising. `pd.isna(x)` is the right check.
- `NaT` (not-a-time). Same idea as NaN but for datetime columns.
- `None` (the Python null). Used for missing values in object columns. Distinct from `NaN`, though pandas tries to paper over the difference. They often display and behave the same way, but `is None` and `isna()` can disagree depending on the column type. When in doubt, use `pd.isna()`.

**In FHIR.** Missing data has two layers. A field that is absent means the receiver does not know. FHIR also has the **`dataAbsentReason` extension**, which lets the sender say *why* a field is absent: `unknown`, `asked-but-unknown`, `temp-unknown` (we will have it later), `not-asked`, `masked` (suppressed for legal reasons), `unsupported` (this system cannot capture it), `as-text` (the data is in a related text field), `error` (the data is bad), `not-a-number` (the math broke). Seven reasons, all different. A well-modeled clinical record distinguishes "no value" from "value unknown for these specific reasons."

**In your exported CSV.** Whatever the exporter wrote. Common offenders:
- Empty string `""` (most spreadsheet exports).
- `NA`, `N/A`, `NULL`, `None`, `nan`, `Unknown`, `.`, `9999`, `999`, `-1`, `--` (every CDW has its own preference).
- A sentinel value at the limit of the assay (`<5` for CRP below limit of quantification).
- A space character (`" "`), invisible to the eye and tested as truthy by every careless filter.

The first cleaning move on any inherited dataset is to read it in, look for every column that contains the same "missing-like" string, and convert it to a proper null. `pd.read_csv(..., na_values=["NA", "NULL", "None", "Unknown", ".", "9999", ""])` does the work. After that, your tool's null is the only kind of null you have to reason about.

## A null is not a value

Most clinical analyses treat a blank cell as if it were a value. The default behavior of every tool you might reach for (pandas, R, Stata, SAS, SQL aggregations) is to silently skip the nulls and compute the statistic over what remains. The number is the mean of the *non-missing* observations. The slide deck calls it the mean of CRP. They are the same number only when the missing observations look like the non-missing ones, which is almost never the case in clinical data.

The first move is to stop treating a null as a value. A null is an absence. The absence has a cause, and the cause determines what an honest analysis is allowed to do next. The three frameworks below name the causes.

---

## The four causes of missing data in clinical extracts

Before the theory, the practice. Most clinical missingness in real extracts is one of four things, sometimes in combination:

### 1. The measurement was not ordered.

The patient had no anti-CCP drawn at the May visit because the rheumatologist already had a positive anti-CCP from 2022 and did not repeat it. The absence is informative: not repeating anti-CCP tells you the rheumatologist trusted the prior result. Treating that absence as random is wrong.

### 2. The measurement was ordered but did not happen.

The lab was ordered but the patient left before the blood draw, the specimen was hemolyzed and rejected, or the tech never got around to it. The absence has nothing to do with what the value would have been. This is the closest clinical missingness gets to "missing at random."

### 3. The measurement happened but did not make it to the extract.

The CRP was drawn and resulted in the EHR, but the cohort export script joined on a primary key that did not match for a subset of patients. The data exists. The export is incomplete. This is an upstream pipeline problem, not a clinical missingness problem. The fix is to chase down the join, not to model the absence.

### 4. The measurement is below the assay's lower limit of quantification.

A CRP analyzer reports "less than 2.0" for values below quantification. The export either drops these rows entirely or stores them as text (which Track 01 caught). The absence is highly informative: it means the value is low. Treating the row as missing pulls the apparent mean CRP up, in a direction that consistently overstates inflammation.

These four causes look identical in the data. The cell is empty. The framework below is how you reason about which cause (or combination) is producing the absences you see.

## MCAR, MAR, MNAR

The classic framework from Donald Rubin's 1976 paper. Three categories. Plain-English definitions, then the clinical interpretation, then how each one behaves under analysis.

### MCAR: Missing Completely At Random

**Plain English.** Whether a value is missing has nothing to do with anything: not the value itself, not the other variables you have observed, not anything in the data. The missingness mechanism is a coin flip.

**Why it is useful as a category.** Under MCAR, the patients with missing values are a random sample of the full cohort. The analysis you would do if those rows were present produces the same estimate (with wider confidence intervals because of the smaller N). Dropping the rows is honest.

**Why it is almost never true in clinical data.** MCAR requires that no clinical signal predicts whether the value is missing. In practice, almost every clinical missingness has a signal. Sicker patients miss visits. Healthier patients skip follow-up labs. Patients with insurance changes get re-coded mid-study. There is always something.

**The closest real example.** Specimen hemolysis. A subset of CBCs are rejected because the sample was handled wrong in transit. The signal that determines which CBCs hemolyze is a property of the transport, not the patient. Approximately MCAR.

### MAR: Missing At Random

**Plain English.** Whether a value is missing depends on other variables you *did* observe, but not on the missing value itself once you condition on what you observed.

**Why it is useful as a category.** MAR is the category most rigorous analyses operate under. "Missing depends on observed variables" does not mean the analysis can ignore missingness. It means the analysis can *correct for* missingness using those observed variables. Multiple imputation, inverse probability weighting, and the E-M-style approaches all rest on MAR.

**Why it is the most common honest assumption.** Most clinical missingness has structure that the rest of the dataset can describe. A 70-year-old with three comorbidities and twelve visits is more likely to have a missing 30-day follow-up than a 35-year-old with one comorbidity and three visits. Age, comorbidity, and prior visit count are all in your data. The missingness depends on the observed covariates, not on the missing 30-day status itself. MAR.

**The clinical worked example.** Ms. Reyes hypothetically misses her July 2024 CRP because she rescheduled the appointment due to a job change. The "missing" is correlated with employment status (observed in the social history) but not with the CRP value she would have had if drawn. Conditioning on employment status, the missingness is random. MAR.

### MNAR: Missing Not At Random

**Plain English.** Whether a value is missing depends on the missing value itself. The reason this CRP is not in the data is the same reason it would have mattered.

**Why it matters most.** MNAR breaks complete-case analysis the hardest, because no amount of conditioning on observed variables can fix it. The information needed to correct the bias is in the missing values themselves, which you do not have.

**The clinical worked examples are everywhere.**

- **Below limit of quantification.** A CRP analyzer reports "below 2.0" as missing. The value is missing *because it was very low*. The mean of the non-missing CRPs overstates inflammation, and there is no way to recover the right mean from the non-missing data alone.

- **Patients who stop coming to clinic because they feel well.** A registry tracks RA disease activity. Patients in remission see less reason to come in. The "missing" disease activity scores are systematically the low ones. Mean DAS28 across the cohort, computed on the non-missing values, overstates disease activity. Patients who stop coming because they feel sick produce the opposite bias. Either way, the missingness depends on the unobserved value.

- **Adverse-event monitoring.** A trial protocol asks patients to report any adverse event. Patients who experience an embarrassing or stigmatized adverse event are less likely to report it. The missing reports are not a random subset of all adverse events. They are the ones with the characteristic that made reporting harder.

MNAR is the category where the honest answer is sometimes "the analysis cannot be done with the data we have." That is worth knowing, because then you can argue for the data collection that would let it be done.

## What complete-case analysis silently assumes

The default behavior of nearly every analysis tool, when it encounters a row with missing values, is to drop the row. This is called **complete-case analysis** or **listwise deletion**.

Complete-case analysis is unbiased under MCAR. Drop a random subset of rows from a random sample, and the remainder is still a random sample.

Under MAR, complete-case analysis is biased in general, but the bias can be removed by conditioning on the observed variables (the standard approaches are inverse probability weighting and multiple imputation).

Under MNAR, complete-case analysis is biased and cannot be corrected from the observed data alone. The bias is in the direction of the values that are not there.

The honest version of every clinical analysis includes an answer to the question: which kind of missingness do I have, and which kind am I assuming? Most analyses assume MCAR by default (the default of every tool), and most clinical missingness is at least MAR and usually has MNAR components. The mismatch is the source of most "the analysis ran but the answer is wrong" failures.

## Imputation: the menu

Imputation means filling in the missing cells with plausible values, then proceeding with the analysis as if the data had been complete. Every approach has a name, an assumption, and a characteristic failure mode.

### 1. Mean / median / mode imputation

**What it does.** Replace each missing value with the column's mean (for continuous), median (for skewed continuous), or mode (for categorical).

**Assumption.** The missing values would, on average, have looked like the observed values. Effectively MCAR.

**Failure mode.** Reduces variance (every imputed cell sits exactly at the mean, which makes the column look more homogeneous than it is). Distorts relationships with other variables (a "mean CRP" cell on a young patient with no comorbidities is implausible; the real value was probably lower). Inflates type 1 error in downstream tests because the confidence intervals shrink artificially.

**When to use anyway.** Quick exploratory analysis. Sensitivity analysis ("what if we filled this with the median?"). Pipeline scaffolding before you build the proper imputation. Never in a published estimate without disclosure.

### 2. Last observation carried forward (LOCF)

**What it does.** For longitudinal data, copy the patient's most recent observed value forward to fill the gap.

**Assumption.** The patient's value stayed approximately the same after dropout. Common in clinical trials, partly by FDA convention, mostly by historical inertia.

**Failure mode.** Creates phantom plateaus. If the patient deteriorated after dropout (which is often *why* they dropped out), LOCF says they were stable. Systematically biases trial estimates toward "the drug works." The FDA has explicitly criticized LOCF as the primary analysis approach in recent guidance. It survives as a sensitivity analysis.

**When to use.** Almost never as a primary analysis. As a sensitivity analysis paired with a tipping-point analysis, to bound how bad the bias could be.

### 3. Regression / model-based imputation

**What it does.** Build a model of the missing variable using the other variables in the dataset. For a missing CRP, fit a regression of CRP on age, ESR, joint count, etc., among patients with all four observed. Use the model to predict the missing CRPs.

**Assumption.** MAR. The model captures the structure that explains why some patients have missing CRPs (and would also have predicted what the CRP would have been).

**Failure mode.** Underestimates uncertainty. The imputed values are point estimates from the model, so they look more confident than they are. The downstream analysis treats imputed and observed values the same, but they are not the same. The imputed values come with prediction uncertainty that has been thrown away.

**When to use.** Quick MAR imputation for exploratory work. Replaced in production by multiple imputation, which fixes the uncertainty problem.

### 4. Multiple imputation (MICE)

**What it does.** Multiple Imputation by Chained Equations. Build a model for each missing variable; generate not one imputed value per missing cell but *many* plausible values, each one drawn from the model's posterior. Run the analysis on each of the resulting "complete" datasets. Pool the results using Rubin's rules, which correctly combine the within-imputation and between-imputation variance.

**Assumption.** MAR. (Multiple imputation does not fix MNAR by itself.)

**Why it is the modern default.** Restores the uncertainty regression imputation throws away. Handles complex patterns of missingness across multiple variables (each variable gets imputed in turn, conditional on the current imputed values for the others). Produces honest standard errors.

**When to use.** Most analyses with non-trivial missingness on MAR-or-better data. Implemented in `sklearn.experimental.IterativeImputer`, R's `mice` package, Stata's `mi`. The implementation is well-trodden. The hard part is choosing the imputation model (predictors, transformations) thoughtfully.

### 5. Don't impute: keep missing as information

**What it does.** Do not fill the missing values. Instead, add a binary indicator column (`crp_missing = True/False`) and let the downstream model use both. In FHIR terms, this is what `dataAbsentReason` is for: not "the value was X" but "the value was missing for reason Y."

**Assumption.** Missingness is itself signal. The reason the cell is empty tells you something the model can use.

**Why it can work.** For MNAR data, the indicator captures the bias the imputation cannot fix. A tree-based model handling "missing" as its own branch is doing roughly the same thing. In some clinical contexts (which patients did not get a recent CRP?), the missing column is the variable you wanted.

**Failure mode.** Loses the original value entirely. If you also want to use the value when present, you need both columns (the value plus the indicator). The indicator-only approach works for models that handle the loss gracefully (trees, regularized regressions). It does not work for plain linear regression that needs every patient to have a value.

### 6. Inverse probability weighting (IPW)

**What it does.** A different paradigm. Do not impute. Run the analysis on complete cases, but weight each observation by the inverse of its probability of being observed. Patients with a high probability of being missing (but who happened to be observed) get up-weighted, so they stand in for the missing patients with similar characteristics.

**Assumption.** MAR. You need a good model for the probability of being observed.

**When to use.** Survey analysis (where IPW originated), causal inference, longitudinal analyses with informative dropout. Equivalent under some conditions to multiple imputation; complementary under others.

## Drop or keep? A practical decision framework

The "should I drop this column?" question comes up earlier than the imputation question, and it determines what imputation you even need to do.

### Drop a column when:

- **Critical missingness.** The column has more than 50% missing in the data you need (rule of thumb, not a rule; the right cutoff depends on how load-bearing the variable is for your analysis). Imputing more than half a column from the rest is asking the rest to do too much work.
- **The column is non-essential.** You included it from the export by default but the analysis does not use it. Drop it; missingness in unused columns is somebody else's problem.
- **The column is so corrupted that imputation is not credible.** A "race" column with 60% missingness and 30% miscoding cannot be saved by imputation. It can be reported descriptively and excluded from inferential modeling.
- **The column duplicates information that is complete elsewhere.** Two CRP columns from different upstream systems, one 90% complete and one 30% complete: keep the complete one, drop the other (after auditing that they agree where both are present).

### Keep a column when:

- **It is load-bearing for the question.** If the analysis is "what predicts DAS28 trajectory?" and DAS28 has 35% missingness, you cannot drop it. Handle the missingness with imputation or with a model that handles missingness natively, and defend the choice.
- **Missingness itself is informative.** A column where the missing values are clinically meaningful (which patients did not have a CRP drawn at follow-up, indicating disengagement) should be kept *and* exposed via a missing-indicator column.
- **The column is rare but informative.** A genetic test result that is missing in 80% of patients but predictive in the 20% who have it. Drop the column for everyone-else analyses. Keep it for the subgroup analyses that hinge on it.

### Drop rows (complete-case analysis) when:

- **Missingness is plausibly MCAR.** A small fraction missing across uncorrelated columns. Complete-case is honest.
- **The cohort is large enough to afford the loss.** 5% rows dropped from a cohort of 10,000 is fine. 5% rows dropped from a cohort of 200 is concerning.
- **The analysis is a quick descriptive characterization, not an inferential one.** Means and proportions for the complete cases are publishable with disclosure. Estimates for the population from biased complete cases are not.

### Don't drop rows when:

- **Missingness is patterned.** Even one MNAR column, dropped via complete-case, biases the analysis in the direction of the values you lost.
- **The cohort is small.** Multiple imputation preserves N at the cost of computational complexity. Complete-case throws away information you cannot get back.

## A practical inventory move

When you inherit a dataset, before you analyze it:

1. **Convert all missing-like strings to proper nulls.** `pd.read_csv(..., na_values=["NA","NULL","Unknown",".","9999",""])`.
2. **Compute the missingness rate by column.** Which columns have any missing values, and what fraction of rows are missing?
3. **Look at the rows with missing values.** Are they clustered in a way that has a clinical story (one site, one time period, one subgroup)? If yes, the missingness is structured, and complete-case analysis is biased.
4. **Ask whoever knows the data.** "These two hundred rows have missing CRP. What happened?" The answer often surfaces causes 1 through 4 from earlier. The MCAR/MAR/MNAR framework is then how you reason about what to do about each one.
5. **Decide drop or keep per column.** Use the framework above.
6. **Decide drop rows or impute.** Use the framework above.
7. **If imputing, pick a method on purpose.** Mean/median (quick scaffold only). Regression (MAR, fast, throws away uncertainty). Multiple imputation (MAR, modern default, preserves uncertainty). Missing-as-indicator (when missingness is signal). LOCF (almost never).
8. **Document every decision in plain English.** "We dropped the `serum_iron` column because 67% of values were missing and the variable is not load-bearing for the disease-activity analysis." That sentence is the audit trail.

The interactive in the notebook walks each mechanism on Ms. Reyes's synthetic CRP cohort, then applies each imputation strategy to see which recover the truth and which do not.

## What this track does not do

- **Sensitivity analysis under MNAR.** Pattern-mixture models, tipping-point analysis, delta-adjustment: the appropriate techniques for analysis when you suspect MNAR and need to test how badly the conclusion changes. These build on the framework here.
- **Imputation at scale across longitudinal data.** When the missingness pattern itself varies over time (informative dropout, intermittent missingness), the analysis becomes a longitudinal modeling problem that goes beyond Track 03.
- **Production-quality MICE implementation.** The notebook demonstrates the idea on a small synthetic dataset. Real MICE on real data has implementation choices (which predictors, which transformations, how many iterations, how many imputations) that course 07 picks up.

The framework is the contribution. Once you can name which kind of missingness you have, choose drop or keep on principle, and pick an imputation method on purpose, the rest is implementation. Without the framework, every approach is the same suggestion you Googled.
