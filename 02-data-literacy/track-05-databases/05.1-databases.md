# What a database actually is

A reference companion to the notebook. Read it first, after, or skip it.

---

## The one-sentence difference

A **spreadsheet** is a tool that lets you type values into cells and do arithmetic on them. Anything goes. The spreadsheet has no opinion about what should be in any given cell.

A **database** is a system that *defines* what may be in each cell, refuses to store anything that violates the definition, and provides ways to query the stored data efficiently and concurrently.

The spreadsheet trusts you. The database does not trust anyone, including you, including the application writing data to it. That mistrust is the feature.

---

## The relational model in 200 words

Edgar Codd published the relational model in 1970. The idea is short:

- Data lives in **tables** (also called relations).
- Each table has named **columns** with declared types.
- Each row is one **observation** (Track 02 will sound familiar).
- Tables relate to each other through **keys**: a column whose values appear in another table's column, allowing rows to be linked.
- Operations on tables (select, project, join, union, intersect) produce other tables, so the result of any query is another table you can query again.

That is it. Every relational database (PostgreSQL, MySQL, SQLite, Oracle, SQL Server, BigQuery, Snowflake, Clarity, Caboodle) is an implementation of this model. The SQL language is the standard way to ask questions and make changes.

The reason this matters clinically: a clinical research warehouse is a relational database. So is an EHR's back-end. So is your CDW. The tables, columns, and joins of Track 04 are not pandas constructs that happen to look like a database; they are the database, projected into pandas for one analyst's use.

## What a schema is

A **schema** is the published contract of a database: which tables exist, which columns each one has, what type and constraints each column carries, and how the tables relate. The schema is written in **DDL** (Data Definition Language): the `CREATE TABLE` and `ALTER TABLE` statements.

A minimal clinical schema with three tables:

```sql
CREATE TABLE patient (
    patient_id     TEXT PRIMARY KEY,
    date_of_birth  DATE NOT NULL,
    sex            TEXT NOT NULL CHECK (sex IN ('male','female','other','unknown'))
);

CREATE TABLE encounter (
    encounter_id   TEXT PRIMARY KEY,
    patient_id     TEXT NOT NULL REFERENCES patient(patient_id),
    encounter_date DATE NOT NULL,
    encounter_type TEXT NOT NULL CHECK (encounter_type IN ('inpatient','outpatient','ed','telehealth'))
);

CREATE TABLE observation (
    observation_id  TEXT PRIMARY KEY,
    encounter_id    TEXT NOT NULL REFERENCES encounter(encounter_id),
    patient_id      TEXT NOT NULL REFERENCES patient(patient_id),
    loinc           TEXT NOT NULL,
    value_num       NUMERIC,
    unit            TEXT,
    observed_at     TIMESTAMP NOT NULL,
    UNIQUE (encounter_id, loinc, observed_at)
);
```

Read carefully. The schema is doing five jobs at once:

1. **Naming the tables and columns.** `patient`, `encounter`, `observation`. The names are the vocabulary the rest of the system uses.
2. **Declaring types.** `patient_id TEXT`, `date_of_birth DATE`, `value_num NUMERIC`. Track 01's question ("what type is this column?") is answered, definitively, in the schema. There is no ambiguity.
3. **Specifying which columns are required.** `NOT NULL` means the column cannot be null. `patient_id`, `date_of_birth`, `sex` must be present for every patient row.
4. **Restricting allowed values.** `CHECK (sex IN ('male','female','other','unknown'))` says the schema knows what FHIR's gender value set is and will reject anything else.
5. **Declaring relationships.** `REFERENCES patient(patient_id)` is a foreign key: every `encounter.patient_id` must exist as a `patient_id` in the `patient` table. The database will refuse to create an encounter for a patient who does not exist.

This is the contract. Any data that violates the contract never enters the database. The data inside is, by construction, internally consistent in every way the schema describes.

## The six constraint types

Each constraint catches a different class of error before the data lands. Each one is worth knowing by name.

### 1. Type

The most basic. A column declared `NUMERIC` rejects `"<2.0"`. A column declared `DATE` rejects `"April 17, 2024"` unless the database can parse it. The Track 01 type problem is caught at insert time, not at analysis time. The cost is upfront: the loader has to clean the data before insert. The benefit is that every analyst downstream gets typed data for free.

### 2. NOT NULL

Declares that a column must have a value. `patient_id NOT NULL` means an encounter without a patient is not a legal encounter, and the database refuses to create one. Catches the Track 03 structural-blank problem at the schema layer.

### 3. UNIQUE

Declares that the values in a column (or combination of columns) must be distinct. A clinical example: `(encounter_id, loinc, observed_at)` must be unique in the `observation` table. Two CRPs with the same encounter, code, and timestamp cannot coexist. If the loader tries to insert one, it is either a duplicate from a flaky pipeline (catch and skip) or a legitimate second measurement at a slightly different time (the timestamps should differ; fix the timestamp).

### 4. PRIMARY KEY

Declares the column (or combination) that uniquely identifies each row. Combines `UNIQUE` and `NOT NULL`, plus a few performance promises. Every well-designed table has a primary key. The primary key is the natural target of foreign key references from other tables.

In a clinical schema, the primary key of each table is the *intended unit of analysis* at that table's grain: a `patient_id` per patient, an `encounter_id` per encounter, an `observation_id` per observation.

### 5. FOREIGN KEY

Declares that values in this column must exist as primary keys in another table. The relational glue. `encounter.patient_id REFERENCES patient(patient_id)` means every encounter must point at an existing patient. The database refuses to insert an encounter for a patient that does not exist, and refuses to delete a patient who has encounters (unless you tell it to cascade the delete, which is its own decision).

This single constraint eliminates a large class of clinical-data bugs: encounters without patients, observations without encounters, prescriptions without medications. The orphan-row problem is structurally impossible inside a foreign-key-constrained schema.

### 6. CHECK

Arbitrary boolean condition that must hold for every row. `CHECK (sex IN ('male','female','other','unknown'))` enforces a value set. `CHECK (date_of_birth <= CURRENT_DATE)` enforces no future birthdays. `CHECK (value_num >= 0 OR loinc IN ('temperature_C'))` enforces "no negative numbers except for the labs where negative makes sense."

`CHECK` is where domain knowledge gets baked in. A schema designer who knows clinical data adds `CHECK` constraints for things like "diastolic must be less than systolic," "discharge date must be on or after admit date," and "discontinue date must be on or after start date." Each one is a class of bug that no application can introduce.

## What you get for the trouble

The cost of constraints is upfront: the people writing data have to satisfy them. The benefit lands every time the data is read.

- **Data integrity.** Every row in the database, by construction, passes every constraint. Cohort definitions are stable. Joins behave. The "wait, why are there encounters for a patient who does not exist?" question is impossible.
- **Referential consistency.** Foreign keys mean every reference is real. A medication points at a patient who exists. An observation points at an encounter that exists. Cascades and restrictions on delete keep this true over time.
- **Performance via indexes.** A primary key is automatically indexed. Foreign keys are usually indexed. Joins on indexed columns are fast even at scale. The query optimizer uses the schema's type and constraint information to plan queries efficiently.
- **Concurrent access.** Multiple users reading and writing at the same time, with transactions that either fully succeed or fully roll back. A spreadsheet with two people editing is a bug. A database with two people editing is the normal case.
- **Durability.** Power loss in the middle of a transaction does not corrupt the database. The transaction either committed (and is durable) or it did not (and the database is in its previous consistent state). Spreadsheets do not have this guarantee.
- **Auditability.** Most clinical databases track who changed what, when, with row-level audit logs. The data inside has a known history.

## A schema for the running patient

The CLAUDE.md spec for this curriculum points at three clinical informatics schemas a reader of this course will eventually need to understand:

- **Operational EHR schemas** (Epic Clarity, Cerner Millennium). Tables shaped by what the EHR needs to *operate*: render the chart, generate a bill, send an order. Wide tables, vendor-proprietary, designed for transaction throughput. Tracks 01 through 04 of this course are largely about wrangling extracts out of these schemas.
- **FHIR** (course 06). Not a database schema per se; an interchange schema. JSON-shaped resources that map roughly onto a relational schema for storage, but whose primary purpose is to travel between systems. Adds clinical semantics on top of the relational model: a `Patient` resource is not any table with a primary key, it is the FHIR `Patient` resource.
- **OMOP CDM** (course 07). A clinical research warehouse schema designed by the OHDSI community. Standardized tables: `person`, `visit_occurrence`, `condition_occurrence`, `drug_exposure`, `measurement`, `observation`. The same data structured the same way across institutions, so an analysis written once works against any OMOP database. Adds the OHDSI standardized vocabulary on top of the relational model.

All three rest on the relational thinking in this track. The constraints are the same constraints. The schemas are the same kind of contract. The clinical semantics are layered on top, not in place of.

## A practical schema-reading move

When you inherit a clinical database, before you start querying it:

1. **Get the schema.** Most databases let you ask for the DDL of a table (`pg_dump --schema-only`, `SHOW CREATE TABLE`, `\d table_name` in psql).
2. **Read the column types.** Track 01 questions get answered here.
3. **Read the constraints.** The `NOT NULL`s tell you which fields are required; the `CHECK`s tell you what values are allowed; the `UNIQUE`s tell you what's expected to be distinct.
4. **Read the foreign keys.** They are the map of the data. The references show you which tables depend on which, and how the joins are supposed to work.
5. **Look for `ENUM` or value-set tables.** Many schemas store the allowed values for a categorical column in a separate small table, with a foreign key from the main table. Read those too. They are often the cleanest way to learn the system's vocabulary.

After this, you can predict what every join will do, what every analysis will fail on, and what every dropdown in the application is showing the user.

## What this track does not do

- **SQL syntax.** Course 07 teaches SQL from first principles, clinical questions first. This track introduces what a schema is, not how to query it.
- **Normalization theory** (1NF through BCNF). The formal theory of why tables look the way they do. Worth knowing if you design schemas; out of scope for this course.
- **Indexing and query performance.** Course 07 territory.
- **NoSQL databases.** Document stores (MongoDB), key-value stores (Redis), graph databases (Neo4j). Course 07's last track covers graph databases at the conceptual level for clinical use cases.

This track is the relational rung. Course 06 (FHIR) and course 07 (OMOP, SQL) are where you climb the next rungs. Without the relational rung in place, those courses feel like a list of arbitrary names. With it, they feel like clinical specializations of one underlying idea.
