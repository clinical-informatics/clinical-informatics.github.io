## What abstraction is

Decomposition (Track 01) takes a problem apart. Patterns and edge cases (Track 02) put it back together while watching the trades. Abstraction is the third move, and the one that lets a rule scale: the decision about what to leave out.

A clinical model with everything in it has the same problem as a note with everything in it. Too much information, no signal, impossible to monitor, brittle to data quality, and nearly always biased in ways nobody has the bandwidth to surface. The skill of abstraction is choosing, out of the hundreds or thousands of features available, the small set that the rule actually needs.

Every feature you include is a debt: data quality, drift, monitoring, explanation, equity surveillance. Every feature you exclude is a bet that the rule will work without it. The discipline is making both decisions deliberately, with written reasoning you could defend to a reviewer.

## Why parsimony matters in clinical models

1. **Auditability.** A model with a dozen features can be inspected by a human. A model with twelve hundred cannot. When the model fails in production, and it will, someone has to identify which feature drifted. Smaller is forgivable.
2. **Equity surveillance.** Subgroup performance must be monitored against every feature category. Fewer features means fewer categories to check, and fewer ways for bias to enter the model without anyone noticing.
3. **Data quality dependency.** Every feature is a dependency on a data source. A model that uses two hundred features fails two hundred different ways when an EHR upgrade breaks a flowsheet field. Smaller is more durable.
4. **Explanation to clinicians.** A model that case management is supposed to act on has to be explainable to case management. A twelve-feature model fits on one slide. A twelve-hundred-feature model cannot be explained at all.
5. **Drift detection.** Drift is detected by watching feature distributions move. Fewer features means more sensitive drift detection and fewer false alarms about model decay.

These are deployment requirements, not aesthetic preferences. A model that cannot be audited, explained, or monitored will not survive its first incident.

## Five categories of features to consider dropping

1. **Leaky features.** Data points that include information only available after or around the outcome you are predicting. The classic example in a 30-day readmission model is whether the patient attended their 7-day follow-up appointment. That fact lives inside the same time window the model is supposed to predict, and its predictive power is largely an artifact of leakage. Leaky features inflate offline performance metrics and quietly fail in deployment, where the leaky signal is not available at scoring time. Leakage is a bug.

2. **Equity-flagged features.** Race, ZIP code, insurance class, ADI (Area Deprivation Index), primary language. These features often carry real predictive signal, partly because they proxy for structural inequity. Including them without justification means the model encodes that inequity and operationalizes it. Including them with explicit, written justification (e.g. "we use ADI as an SDOH proxy because the deployment goal is to direct social-work resources, not to ration clinical attention") is sometimes appropriate. The default to avoid is including them because they improve the AUC, with no thought given to what the AUC was measuring.

3. **High-missingness features.** A feature missing more than forty or fifty percent of the time is effectively absent in deployment. Imputation can paper over the gap on a development set but produces a model that runs on imputed values more than on real data. What the model is using is the imputation strategy, not the underlying signal.

4. **Redundant features.** Two features that capture the same underlying signal do not both belong in the model. Charlson and HCC categories overlap heavily; LACE acuity and discharge disposition overlap heavily; HbA1c at admission and prior diabetes diagnosis overlap heavily. Pick one. The duplicate carries debt without adding signal.

5. **Cosmetic features.** Features that are predictive in isolation but contribute nothing once the right features are in. They add a deployment dependency, an audit obligation, and a monitoring line without buying performance. The discipline is to test feature importance with and without each one, and to drop any that do not move the dial.

## The dual of decomposition

Decomposition asks: *what are the parts of this thing?* Abstraction asks: *which parts can be discarded?*

The two moves work together. Decompose to make the parts visible. Abstract to make them few enough to manage. A rule that has been decomposed but not abstracted is exhaustive and unusable. A rule that has been abstracted without first being decomposed is parsimonious by accident.

## What a defensible feature list looks like

When a feature selection pass is finished, the supporting document should answer five questions for every feature on the list:

1. What is this feature, in one plain-English sentence?
2. Where does it come from in the chart? Which source system, which field, with what latency?
3. What is the predictive signal it carries, and at what marginal cost in deployment complexity?
4. What equity concerns, if any, attach to it, and what is the explicit justification for including it anyway?
5. What happens to the model if this feature drifts, disappears, or starts being captured differently?

If you can answer all five for every feature, the model is auditable. If you cannot, the model is not deployment-ready, no matter how well it performs on a held-out validation set.

## What published clinical scores look like

The LACE index (van Walraven et al.) predicts 30-day readmission and death using four variables: length of stay, acuity of admission, Charlson comorbidity index, and emergency department visits in the prior six months. The HOSPITAL score uses seven. The PARR-30 uses around twelve. None use eight hundred features.

These scores live in real hospitals partly because they perform and partly because they are small enough to live in a real hospital. A score that cannot fit on one slide cannot be deployed against a real workflow.
