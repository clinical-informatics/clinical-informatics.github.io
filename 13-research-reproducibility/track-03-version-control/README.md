# Track 03: Version control without coding

The `analysis_FINAL_use_this_one.csv` problem from Track 02 has a clean solution, and it is not better discipline about file names. It is a tool that records every version of a file automatically, keeps them all, and lets anyone recover any prior state or compare any two states. That tool is version control, and the dominant one is Git.

The track explains Git in plain English and explains the one problem it solves: keeping the complete history of a project so that no version is ever lost and any two versions can be compared. It draws the distinction that confuses most newcomers: **Git** is the version-control system (the history-keeping tool), and **GitHub** is a website that hosts Git projects and adds collaboration features on top of them. The track covers the three concepts a clinician collaborating on a data project actually needs (the **commit** as a recorded snapshot with a reason attached, the **issue** as a tracked unit of work and discussion, and the **pull request** as the review-and-approve surface for a proposed change), and it makes the case that the issue and the pull request are usable as collaboration and project-management tools without writing a single line of code. No commands are run in this track. The notebook walks a project's commit history and a pull-request review as readable artifacts.
